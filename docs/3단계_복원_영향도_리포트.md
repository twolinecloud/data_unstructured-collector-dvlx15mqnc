# 비정형 파이프라인 3단계 복원 — 영향도 점검 리포트

- 작성: 2026-10-01
- 대상: unstructured-collector(이 저장소) · log-collector · admin-fe · (확인만) admin-api · data_HelmChart
- 결정: 클라우드 전송·비식별화(에이전트 커넥터)를 빼고 온프레미스 **제논(Zenon)** 으로 넘긴다.
  `/k8s/unstructured_collector/xenon` 은 삭제됐고 앞으로 결과를 남기지 않는다.

## 1. 단계 정의 (변경 전 → 후)

| | 변경 전 (4단계) | 변경 후 (3단계) |
|---|---|---|
| T2 체인(비정형) | COLLECT 1 → ANALYZE 2 → DEIDENT 3 → SEND 4 | **COLLECT 1 → ANALYZE 2 → SEND 3** |
| 수집 COLLECT | 대상 조회 · 브로커 추출/ESB 수신 · 복호화 | 같음 |
| 정제/분석 ANALYZE | STT | 같음 |
| 비식별 DEIDENT | 커넥터 `deidentEnabled` 수행/단순 전달 · T5 기록 | **없음** |
| 적재/전송 SEND | PV `xenon/{kind}/{execId}/` 저장 + 커넥터 이관 | **제논 수신 API 로 multipart 전송**(PV 에 남기지 않음) |
| 처리 이력 | T1 · T2(4행) · T4 · T5 | T1 · T2(3행) · T4 |

> 복호화는 예전부터 COLLECT 로 집계된다(확보 워커가 받은 파일을 STT 워커가 복호화 — `FROM_ANALYZE` 재처리가 복호화 산출물을 쓴다).
> 시뮬레이터 문구도 이 집계에 맞췄다.

## 3. 로그 테이블 적재 측 부작용 점검

### 3-1. T2 단계 순번 · STEP_LOG_ID

- STEP_LOG_ID = `EXEC_ID + 순번 2자리`. 새 배치의 SEND 는 `…03`(예전 `…04`). 재처리도 **새 EXEC_ID** 로 열리므로 옛 배치 행과 겹치지 않는다.
- **배포 순서**: 로그 컬렉터를 먼저(완료 — dev 푸시) → 수집기. 반대로 하면 옛 컬렉터가 SEND 를 4번으로 적고 3번(DEIDENT)이 비어 타임라인에 빈 칸이 생긴다
  (데이터 손실은 없다 — 순번만 다르다).
- 옛 수집기 이미지가 혹시 DEIDENT 를 부르면 새 컬렉터는 체인 밖 순번(14)으로 적는다 — 3단계 뒤에 정렬되어 화면을 깨지 않는다(`StepTypeTest`).
- `logs.mock-steps.enabled`(빠진 단계를 모의 SUCCESS 로 채움)는 체인을 따르므로 비정형에 DEIDENT 를 더는 채우지 않는다.
- 단계 가드(COLLECT·CLEANSE 재진입 금지)는 영향 없음.

### 3-2. T4 · T5 · 정합성 규칙

| 항목 | 영향 |
|---|---|
| T4 `FILE_PATH`(파일별 결과 위치) | PV 경로 대신 `zenon:mock/{file}` 또는 `zenon:{endpoint}/{file}` — **이 값을 경로로 열어 쓰는 하류가 있다면 바뀌어야 한다**(사내 확인 결과 admin-api 는 표시만 함) |
| T5 `TB_DEIDENT_SEND_LOG` | 비정형 새 배치는 **행이 생기지 않는다**. 옛 배치 행은 그대로(삭제 안 함) |
| T8 비식별 결과 상세 | 비정형은 원래 없음 — 영향 없음 |
| 정합성 `SUCCESS_CNT == Σ(T3·T4·T5)` | 비정형은 T4 만으로 맞춘다 — 영향 없음 |
| 시험 데이터 삭제(`DELETE /logs/test-data`) | T5 도 계속 지운다(옛 TST 이력) — 영향 없음 |

### 3-3. 조회 측(admin-api · admin-fe)

- admin-api `GET /batch-exec-logs/{execId}/files`(비정형 파일 목록)는 T4 에 T5 를 **LEFT JOIN** 하고 상태를
  `COALESCE(T5.SEND_STS_CD, T4.PROC_STS_CD)` 로 낸다 → T5 가 없어도 **T4 상태로 정상 표시**된다. 다만 새 배치는
  "비식별화 건수"·"JSON 뷰어"(T5 의 `PII_ITEM_CNT`·`AFTER_DATA`)가 빈다 — 3단계에서는 의도된 결과다.
- admin-fe 배치 상세는 비정형 카드가 3개다. **옛 배치의 DEIDENT 단계 행은 카드로 보이지 않는다**(데이터는 남아 있음).
  옛 이력까지 4칸으로 보여야 한다면 그때 슬롯을 유형·시점별로 나눈다.
- 대시보드 카드 노드는 로그 컬렉터 체인을 따르므로 비정형 3노드가 된다.

## 4. 재처리 로직 · 시뮬레이터 시나리오 점검

| 실패 단계 | 보존물 | 재처리 | 확인 |
|---|---|---|---|
| COLLECT(브로커 주소 장애) | 없음 | `FULL` — 멱등 표식이 없어 다음 배치가 다시 처리 | 시나리오 1 |
| ANALYZE(STT 500/Timeout) | 복호화 오디오 `xvram/decoding/decrypted_*` | `FROM_ANALYZE` — 확보·복호화 스킵, STT 부터 | 시나리오 2 |
| SEND(제논 500/Timeout) | 전사 `stt_temp/{execId}/*.json` | `FROM_SEND` — STT 없이 보존된 전사로 제논 재전송 → 보존물 삭제 | 시나리오 3 · `SimulatorWorkflowTest.sendFailureResumesFromTranscript` |

- `xenon/` 에는 어떤 경로로도 쓰지 않는다(`VoiceCollectE2ETest` 가 폴더 미생성을 확인).
- `FROM_DEIDENT` 는 없앴다 — 옛 클라이언트가 보내면 400(알 수 없는 enum).
- 재처리 창(이틀)에는 첫 실행이 다루지 않은 주기용 SIM 도 들어온다 → 시나리오 3 재처리가 "실패 10건 + 주기 4건 = 14건" 을 보내는 것은 정상.
- 로컬 실검증(18095, 2026-10-01): 시나리오 3 — 1차 SEND FAIL 10건 · 수신증 0 · 전사 보존 → 재처리 SEND SUCCESS 14건 · 수신증 14 · 보존물 0.

| 파트 | 값 |
|---|---|

## 6. 결정이 필요한 것

1. **`inmate_no` 에 교정번호(CORR_NO)를 그대로 싣는다** — 비식별 단계가 빠졌으므로 제논이 원문 PII(교정번호 · 전사 속 성명/번호)를 받는다.
   온프레미스라 허용된 것으로 보았지만, 가명 ID(`INMATE_PID`)로 바꿔야 하면 `ZenonVoiceDocument` 한 곳만 고치면 된다.
2. **수용자 이미지는 제논으로 보내지 않는다** — 지금은 Admin DB 매핑까지. 규약의 `type=IMAGE` 는 받을 준비만 돼 있다.
3. **제논 실주소·인증** — 확정되면 `ZENON_MODE=REST` · `ZENON_BASE_URL`(+ 필요 시 인증 헤더 추가 개발).
4. **수신증은 수집기 메모리**(최근 500건) — 재기동하면 [제논 전송 확인] 이 비어 있다. 영구 대사가 필요하면 제논 쪽 수신 이력으로 한다.

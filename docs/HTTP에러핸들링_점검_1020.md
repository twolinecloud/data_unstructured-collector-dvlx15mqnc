## 0. 요약 — 메시지는 어디서 뭉개지나

```
커넥터 ──(404/409 + message 정확)──▶ admin-api relay() ──(404/409 + message 보존)──▶ admin-fe 인터셉터 ✗ 본문 버림 ──▶ 화면 catch ✗ 고정 문구
수집기 ──(400/409 + 60자 message)──▶ admin-api BatchRun/Reprocess ──(409→400, 타임아웃·5xx→503)──▶       〃              ──▶       〃
```

1. **가장 큰 구멍은 admin-fe 공통 인터셉터** — 오류 본문(`message`)을 전혀 읽지 않고 상태 코드만으로 고정 문구를 만든다(`src/api/client.ts:9-15, 32-36`). admin-api 5a6a45b 가 실어 보내는 수집기 60자 안내도, 커넥터 404 "보류 중인 전송이 없습니다"도 **어떤 화면에도 닿지 않는다.** [코드]
2. 클라우드 전송 화면은 그 위에 한 번 더 `() => false` 로 삼키고 모든 실패를 "일시적인 네트워크 문제"로 덮는다(`CloudTransferPage.tsx:63, 142-146, 153-157`). [코드]
3. admin-api 는 커넥터 중계(`relay()`)는 잘 나누지만, **수집기 중계(BatchRunClient · ReprocessClient)는 409 를 400 으로, 타임아웃과 5xx 를 같은 503 으로 묶는다.** 바로 실행 중복은 수집기가 200 `accepted:false` 로 답해 admin-api 가 **성공(REQUESTED, execId null)** 으로 돌려준다 → 화면 "바로 실행 완료". [코드 + 문서]
4. "60초 → 503(진행 중일 수 있음)" 설계는 **실제로는 거의 안 나올 가능성이 크다** — admin-api 비동기(Callable) 타임아웃 미설정 → Tomcat 기본 30초에 catch-all **500**, 그 전에 nginx `/api/` 기본 60초 **504** 가 경합. [코드(설정 부재) + 추정(결과)]
5. 세 백엔드(커넥터 · 로그 컬렉터 · admin-api)가 같은 egov 템플릿을 복사해 **catch-all 500 의 본문에 `http_status_code: 503`** 을 넣는다 — 상태 줄과 본문이 어긋난다. [코드]
6. 우리 레포에도 확정 결함 3건 — 커넥터 release `inFlight` 누수(409 고착), 수집기 "로그 컬렉터 장애 = 배치 없음(400)" 오분류, 로그 컬렉터 더미 삭제 500건 초과 = 500. [코드]

## 3. 즉시 적용 가능한 수정 코드 제안

> admin-api · admin-fe 는 **담당자 브랜치에 push 하지 않는다.** 아래는 제안 코드이며, 적용은 사용자 승인 뒤 테스트 브랜치(`_wt/admin-api-test` 등)에서.
> **상태 코드 약속(제안)** — 화면이 이 넷만 가르면 된다.
>
> | 코드 | 뜻 | 화면 |
> |---|---|---|
> | 4xx | 하위가 밝힌 업무 사유 | 백엔드 `message` 그대로(한글일 때) |
> | **504** | 하위 응답 지연 · 비동기 시간 초과 — **처리 중일 수 있음** | "다시 누르지 말고 새로고침으로 확인" + 그 행 버튼 잠시 잠금 |
> | 503 | 하위 미설정 · 연결 실패 · 하위 5xx — 처리 안 됨 | "잠시 후 다시 시도" |
> | 500 | admin-api 자체 오류 | "서버 내부 오류" |
>
> 타임아웃을 503 이 아니라 **504** 로 고른 이유: nginx 가 upstream 시간 초과 때 어차피 504 를 주므로(문제 #5), 화면 규칙이 "504 = 진행 중일 수 있음" 하나로 끝난다. 503 을 타임아웃 전용으로 남기고 싶으면 아래 `GatewayTimeoutException` 대신 나머지(미설정 · 실패)를 502 로 옮기면 된다.
>
> **타임아웃 사슬(안쪽이 먼저 끊겨야 한다)**: 커넥터 read 60s(현행) < admin-api 비동기 70s < nginx `/api/` 75s < 화면 release 80s.

### 3-1. admin-api

**A1. 504 예외 신설 + 처리기** — `exception/GatewayTimeoutException.java`(새 파일)

```java
package egovframework.admin.exception;

import org.apache.logging.log4j.Logger;
import org.springframework.http.HttpStatus;
import org.springframework.lang.Nullable;
import org.springframework.web.bind.annotation.ResponseStatus;
import egovframework.admin.response.ResponseCode;

/** 504 — 하위 시스템이 제때 답하지 않음. 요청은 하위에서 계속 처리 중일 수 있어 503(처리 안 됨)과 구분한다 */
@ResponseStatus(value = HttpStatus.GATEWAY_TIMEOUT)
public class GatewayTimeoutException extends ExceptionBase {
    public static final String MAYBE_RUNNING = "응답이 늦습니다. 처리 중일 수 있으니 다시 누르지 말고 목록을 새로고침해 확인해 주세요.";

    public GatewayTimeoutException(Logger l, @Nullable String message) {
        logger = l;
        errorCode = ResponseCode.GATEWAY_TIMEOUT;
        this.additionalMessage = message;
    }

    @Override
    public int getStatusCode() {
        return HttpStatus.GATEWAY_TIMEOUT.value();
    }
}
```

`response/ResponseCode.java` — `SERVICE_UNAVAIABLE(6000),` 아래에

```java
    /** 하위 시스템 응답 지연 — 처리 중일 수 있다 */
    GATEWAY_TIMEOUT(6001),
```

`exception/ExceptionResolver.java` — `unavailableServiceExceptionHandler` 다음, catch-all 앞에

```java
    /** 504 — 하위 응답 지연 · 비동기 요청 시간 초과. catch-all 에 먹혀 500 이 되지 않게 따로 둔다 */
    @ExceptionHandler({
    GatewayTimeoutException.class,
    org.springframework.web.context.request.async.AsyncRequestTimeoutException.class
    })
    @ResponseStatus(HttpStatus.GATEWAY_TIMEOUT)
    @ResponseBody
    public ErrorResponse gatewayTimeoutExceptionHandler(HttpServletRequest request, Exception exception) {
        ExceptionBase e = exception instanceof ExceptionBase base ? base
```

**F2. 화면 공용 판정 · 문구** — `src/api/errorText.ts`(새 파일)

```ts
import type { ApiError } from "./client";

const HANGUL = /[가-힣]/;

/**
 * 처리 중일 수 있는 실패 — 응답만 늦었고 서버(하위)에서는 계속 돌고 있을 수 있다. 다시 누르지 말고 새로고침으로 확인.
 * admin-api 가 아직 504 로 바뀌기 전에는 503 + 영문 안내("may still be running")로 온다 — 둘 다 받는다.
 */
export const isMaybeInProgress = (e: ApiError) =>
  e.timedOut === true || e.status === 504 || (e.status === 503 && /may still be running|처리 중일 수/.test(e.detail ?? ""));

/** 토스트 설명 — 진행 중일 수 있으면 확인 안내, 서버 사유가 한글(하위 업무 안내)이면 그대로, 아니면 상태 코드별 기본 문구 */
export const describeError = (e: unknown): string => {
  const err = e as ApiError;
  if (isMaybeInProgress(err)) return "응답이 늦습니다. 처리 중일 수 있으니 다시 누르지 말고 목록을 새로고침해 확인해주세요.";
  if (err.detail && HANGUL.test(err.detail)) return err.detail;
  return err.message ?? "요청을 처리하지 못했습니다.";
};
```

> `HANGUL` 검사는 임시 방편이다 — admin-api 자체 4xx 문구가 영문 개발자 문구라(문제 #13) 그대로 띄우지 않으려는 것. A4 처럼 admin-api 화면용 문구가 한글로 바뀌면 검사 없이 `detail` 을 써도 된다.

**C3. 수집기 — 하위 장애를 400 이 아니라 503 으로** — `LogCollectorClient.batchDetail` 이 "없음"과 "못 읽음"을 다 null 로 돌려주는 게 원인. `exchange` 실패를 구분해 주는 변형(`batchDetailOrUnavailable`)을 두고, `planReprocess` · `CloudSendService.plan` 에서 못 읽음이면 `DownstreamUnavailableException` → `AdminLinkController` · `AdminCollectCompatController` 처리기에서 503 `{message:"재처리를 시작하지 못했습니다. 잠시 후 다시 시도해 주세요."}`. `MSG_CHAIN_UNAVAILABLE` · `MSG_SEND_UNAVAILABLE` 두 곳도 같은 예외로. (admin-api 가 5xx message 를 버리므로 A7 의 "5xx 도 message" 와 짝으로 내야 화면까지 간다.)

**C4. 로그 컬렉터** — `DummyBatchService.java:40` 을 `InvalidParameterException` 으로(또는 `ExceptionResolver.java:53-58` 400 목록에 `IllegalArgumentException` 추가) · `LogService.java:97` 을 409(`ResponseStatusException(CONFLICT)`) · `ExceptionResolver.java:209-212` 에 `body.put("message", e.getReason())` 추가(키 통일) · `spring.mvc.async.request-timeout` 명시.

# unstructured-collector 구현 현황

> 기준일 2026-09-30 · 저장소 `data_unstructured-collector-dvlx15mqnc` · 서비스 `unstructured-collector-dvlx15mqnc`(네임스페이스 `data-pipeline`)

## 1. 개요

보라미(교정 업무 시스템)에 쌓이는 **파일 기반 비정형 데이터**를 가져와 분석 가능한 형태로 만드는 수집 서비스다.
정형 데이터는 data-collector 가, 비정형은 이 서비스가 맡는다(PL 결정 2026-09-29 — 옛 voice-collector 에서 이관).

| 대상 | 원천 | 결과물 |
|---|---|---|
| **음성** — 접견 녹음 · 전화 녹음 | 보라미 DB(접견 녹화 파일 · 통화 내역) + XVARM 파일 저장소 | 복호화한 음성의 **STT 텍스트** — 온프레미스 **제논(Zenon)** 으로 전송(PV 에 남기지 않음 · 2026-10-01 3단계 복원) |
| **이미지** — 수용자 사진 | 보라미 DB(수용자 이미지 · 공통파일) + XVARM | 복호화한 **사진 파일** — `{ROOT}/image/{교정번호}/` + Admin DB 매핑(`kcais.tb_src_inmate_photo`) |

`{ROOT}` = 데이터 루트 `/k8s/unstructured_collector`(K8s) · `C:/k8s/unstructured_collector`(Windows 로컬).

## 2. 동작 방식 — Spring Batch 를 쓰는가?

**쓰지 않는다.** 의존성에 `spring-batch` 가 없고 JobRepository(배치 메타 테이블)도 없다. 구성은 이렇다.

| 요소 | 무엇으로 | 비고 |
|---|---|---|
| 기동 | **스프링 `@Scheduled`** (`@EnableScheduling`) — `VoiceBatchScheduler` | 일배치 `voice.batch.daily-cron`(기본 매일 02:00) · 주기배치 `periodic-cron`(10분마다). `voice.batch.schedule-enabled` 로 켜고 끈다 — **개발계는 꺼져 있다**(시뮬레이터·API 로 돌린다) |
| 수동 실행 | REST API — `/api/v1/voice/batches/*`, `/api/v1/image/batches` | 시뮬레이터(`unstructured_collector_simulator.html`)가 이 API 를 부른다 |
| 병렬 처리 | **직접 만든 워커 풀** — `ExecutorService`(고정 크기) | 음성: 확보 워커 · STT 워커 둘로 나눈 생산자-소비자(`Workers`). 이미지: 워커 N 개 |
| 실행 이력 · 단계 기록 | **로그 컬렉터 REST API**(T1 배치 · T2 단계 · T4 파일 건별) | 이 서비스는 로그 DB 커넥션을 잡지 않는다. Spring Batch 의 JobExecution/StepExecution 역할을 T1/T2 가 한다 |
| 재실행 안전(멱등) | 음성: **처리 완료 표식 파일**(PV, `IdempotencyGuard`) · 이미지: 매핑 테이블 **UPSERT** | 같은 건을 두 번 처리하지 않는다 / 다시 돌려도 키 중복이 없다 |
| 동시 실행 방지 | 서비스 안의 실행 중 플래그 | 같은 종류의 배치는 한 번에 하나. 초기 구성은 `replicas: 1` |

왜 Spring Batch 가 아닌가 — 일감이 "DB 에서 대상 목록을 뽑아 건마다 외부 시스템(브로커 · STT · 제논)을 부르는" I/O 대기형이고,
재시작 지점은 건 단위 멱등 표식으로 충분하다. 서비스 규약상 자체 상태 테이블을 두지 않기로 했고(R&R),
실행 이력은 공용 로그 컬렉터(T1 · T2 · T4)에 남기는 것이 표준이라 JobRepository 를 따로 둘 이유가 없었다.

- **브로커와 수집기가 같은 PV 를 붙인다**(RWX). 개발계에는 ESB 가 없어 브로커가 `{ROOT}/esb/meet` 에 파일을 직접 쓰고, 수집기가 그 폴더를 본다.
  PV 는 수집기 차트가 만들고(보존 표시) 브로커 차트는 붙이기만 한다 — 옛 voice-collector 와는 2026-09-30 완전히 분리했다.
- **모드 전환**(시뮬레이터 1번 탭 · 설정): 각 외부 연계를 실제/Mock 으로 바꿀 수 있다.

| 연계 | 모드 | 개발계 |
|---|---|---|
| 원천 조회 | `DIRECT_JDBC`(보라미 DB 직접) · `ESB_HTTP2DB` · `MOCK`(H2) | DIRECT_JDBC |
| 접견 파일 확보 | 브로커 `REST` · `MOCK`(수집기 내장) | REST (브로커 어댑터 DUMMY) |

| 복호화 | `REAL`(RVS 키 AES) · `SKIP` | REAL |

## 4. 음성 수집

### 4-1. 흐름

| 단계 | 하는 일 | T2 단계 |
|---|---|---|
| ① 대상 선별 | 시간창의 접견(`TB_RERD_TFIN_DS`)·전화(`TB_IMPH_UCDR_DS`) 중 **특이수용자** 건 — 공통파일·XVARM 로 FILEKEY 까지 | — |
| ② 멱등 확인 | 처리 완료 표식이 있으면 건너뜀 | — |
| ③ 파일 확보 | 접견: 브로커 `POST /api/v1/xvarm/extract` → 수신 폴더 도착 대기(쓰기 완료까지) · 전화: 파일 연계 수신 대기 | COLLECT (1) |
| ④ 복호화 | 접견 RVS(AES) · 전화 ARIA/AES | COLLECT (1) |
| ⑤ STT | NPU STT(개발계 Mock) · 전화는 보라미 기존 STT 가 있으면 그것을 쓴다 | ANALYZE (2) |
| ⑥ 제논 전송 | 제논 수신 API 에 multipart(file = 전사 JSON · metadata = exec_id·inmate_no·type·file_name) — `zenon.mode` MOCK(기본)/REST. 실패하면 전사를 `{ROOT}/stt_temp/{execId}/` 에 보존하고 그 건은 SEND 실패 | SEND (3) |
| ⑦ 이력 | T1(배치) · T2(단계 3행) · T4(건별 성공/실패·사유 · 전송 위치 `zenon:…`) — 로그 컬렉터 API | — |

> **3단계 복원 (2026-10-01)** — 클라우드 전송과 비식별화(에이전트 커넥터 · DEIDENT 단계)를 빼고 온프레미스 제논으로 넘긴다.
> 로그 컬렉터 비정형 체인도 `COLLECT 1 · ANALYZE 2 · SEND 3` 으로 바꿨다. 영향도: [`3단계_복원_영향도_리포트.md`](3단계_복원_영향도_리포트.md).

### 4-2. 배치 종류와 시간창

| 배치 | 시간창 | 기동 |
|---|---|---|
| 일배치 | 어제 00:00 ~ 오늘 00:00 | cron(기본 02:00) · `POST /batches/daily` |
| 주기배치 | 당일 00:00 ~ 지금(자정 직후엔 지금-20분부터) — 앞에서 놓친 건까지 줍는다 | cron(10분) · `POST /batches/periodic` |
| 바로 실행 | DB 워터마크(마지막 성공 배치의 끝) ~ 지금 | `POST /batches/on-demand` |
| 재처리 · 이어하기 | 실패 · 중단된 건 | `POST /batches/resume` · `/batches/manual` |

창이 겹쳐도 멱등 표식이 같은 건을 두 번 처리하지 않게 막는다.

### 4-3. 워커 · 격리 · 중단

- **확보 워커**(기본 1)가 받아 둔 파일을 **STT 워커**(기본 1, 성능 시험 최대 31)가 집어 간다 — 브로커를 밀어붙이지 않으면서 STT 를 병렬로.
- 한 건의 실패는 그 건만 T4 에 실패로 남기고 다음 건을 계속한다(1,300건 배치가 한 파일 때문에 멈추지 않게).
- **중단**은 파일 수신 대기 중에도 곧바로 먹는다(2026-09-30). 트랜잭션은 DB 작업에만 짧게 — 파일 I/O · STT 동안 커넥션을 잡지 않는다.

## 5. 수용자 이미지 수집

| 단계 | 하는 일 |
|---|---|
| ① 최신 이미지 조회 | `TB_IRIM_BSIF_DS` 에서 `IMAGE_SE_CD='1'`(사진) 중 수용자별 `IMAGE_SN` 최대 1건 |
| ② ③ FILEKEY | `TB_SMSM_CMFI_BS`(DOC_ID) → `ASYSCONTENTELEMENT`(FILEKEY) |
| ④ 수신 · 복호화 | 브로커 추출 → 수신 폴더 → 접견과 같은 RVS 복호화 · 결과가 이미지(매직 넘버)인지 확인 |
| ⑤ 저장 · 매핑 | `{ROOT}/image/{교정번호}/{교정번호}_{순번}.{확장자}`(원자적 덮어쓰기) → Admin DB `tb_src_inmate_photo` **UPSERT** |

- **UPSERT**: PostgreSQL `INSERT … ON CONFLICT (corr_no) DO UPDATE … WHERE 기존 순번 <= 새 순번` 한 문장 — 다시 돌려도 키 중복 없이 있으면 갱신 · 없으면 넣기. 옛 사진은 덮지 않는다(STALE).
- 변경 없는 건(순번·FILEKEY 같고 파일 있음)은 다시 받지 않는다. 건마다 격리 · 매핑은 건당 짧은 트랜잭션 하나.
- 실행: API `POST /api/v1/image/batches`(동기). 스케줄은 아직 없다. 처리 이력은 로그 컬렉터에 아직 남기지 않는다(이미지용 작업 코드 미정).
- `TB_SRC_INMATE_BS.PHOTO_REF` 는 정형 수집기가 다시 쓰므로 별도 매핑 테이블에 두고 필요할 때 일괄 반영한다(`POST /api/v1/image/photo-ref/sync`).

## 6. 시뮬레이터 · 검증 도구

`https://<admin-fe>/unstructured_collector_simulator.html` (로컬 `http://localhost:8085/…`) — admin-fe nginx 가 화면을 내고 `/voice/` 를 이 서비스로 프록시한다.

| 탭 | 용도 |
|---|---|
| 1 | 구성 · 모드 전환 · 연결 확인 |
| 2 | 파이프라인 제어 — SIM 데이터 생성/초기화, 일배치 · 주기 · 바로 실행, 3단계 띠(T2 상태) · [제논 전송 확인](수신증) · 결과 검증 |
| 3 | 장애 · 재처리 시나리오 — 1 수집(브로커 주소) · 2 분석(STT) · 3 전송(제논 500/Timeout → 전사 보존 → `FROM_SEND`) |
| 4 | 기본 부하 검증(확보/STT 워커 · 가상 지연 · Hikari) |
| 5 | 임계 성능(워커 램프업) |
| 6 | 수용자 이미지 수집 검증 — 신규 실행 / 재실행(멱등성) · 의도적 실패 주입 · UPSERT/실패 리포트 · **단계별 실행 기록**(①~⑤ 실제 SQL · cURL · 셸과 결과 — 실행 로그에 실시간, 리포트에 "실행 결과 상세 검증") |

SIM 데이터는 `SIM…`·`SIMIMG…` 접두로만 만들고 지운다. 실제 수집은 SIM 행을 대상에서 뺀다.
상단 [시뮬레이션 데이터 초기화] 는 음성 SIM 과 함께 6번 탭 [SIM 데이터 정리] 와 같은 이미지 SIM 정리(보라미 `SIMIMG…` 행 · Admin 매핑 · 더미 원본 · 저장 사진)까지 한다.
성능 결과 파일(`{ROOT}/perf/history.jsonl` · `image-history.jsonl` · `ramp-history.jsonl`)은 **마지막 실행 한 건만** 남긴다(덮어쓰기 · 2026-10-01).

단계별 실행 기록 API — `GET /api/v1/image/trace?after=<seq>`(일반 수집) · `GET /api/v1/mock/image/perf/runs/current?traceAfter=<seq>`(6번 탭 폴링).
조회(①~③)는 첫 페이지, 건별 단계(④⑤)는 첫 건(표본)만 적는다 — SQL 은 값을 채운 표시용 사본(실행은 바인딩).

## 1. 1단계는 이미 돌았다 — 2026-10-08 시험 결과

`ref/AI-R_문서형식_시험결과.md` 에 개발계 실측이 있다. **다시 처음부터 잴 필요가 없다.**

- API: **`POST /air/api/detect/system/file`** · `masking:true` — **AI-R 파일 API 는 존재하고 동작한다**
- 조건: 개발계 `fsds-air:1.22.0_K8S.0.RELEASE` · **OCR 꺼짐**(`skip-ocr=true`) · 커넥터 개발계 검출 세트와 동일

### 포맷별 결과 (작은 문서 1쪽 · 큰 문서 약 15쪽)

| 형식 | 결과 | 텍스트 추출 | 검출(큰 문서) | 비고 |
|---|---|---|---|---|
| 텍스트(기준선) | 성공 | 100% | 1,066/1,120 (95.2%) | 비교 기준 |
| **docx** | 성공 | 100% | 95.1% | |
| **xlsx** | 성공 | 100% | 94.1% | |
| **pptx** | 성공 | 100% | 94.3% | **느리다** — 15쪽 81.3초(다른 형식 약 30초) |
| **hwpx** | 성공 | **96.0%** | 93.3% | **표 뒤 텍스트 누락** |
| **pdf** | **실패 HTTP 500** | — | — | pdfbox 2.x/3.x 충돌(AI-R 패키지 결함) |

### 이미 드러난 한계 — 이번 기획이 파고들 자리

1. **PDF · HWP 는 못 쓴다.** 파일 탓이 아니라 **AI-R 패키지 결함**이다(라이브러리 두 벌 충돌).
   파수에 조치 요청이 나가 있고 **아직 답이 없다** → 재확인 대상(§2).
2. **HWPX 는 표 바로 뒤 텍스트를 놓친다.** 한글에서 표 다음 문단이 표와 같은 `<hp:p>` 안에 이어지면
   추출하지 않는다(큰 문서에서 제목 39개 누락 → 어절 96%). **그 자리에 개인정보가 있으면 검출도 마스킹도 안 된다.**
3. **마스킹 후 남은 건 대부분 '표의 이름 칸'** — 문장 없이 이름만 있는 셀을 딥러닝이 놓친다(pptx 12건으로 최다).
   → 지적하신 **표 구조 문제가 이미 관측됐다.** 이번엔 그걸 **의도적으로 재는 것**이 과제다(§4).
4. pptx 는 내부 부분(슬라이드 XML)마다 따로 검출을 돌려 **슬라이드 수에 비례**해 느리다.
5. 처리 시간은 거의 **딥러닝 검출**이 정한다(약 1.3초/1,000자). 파일 해석은 1초 안팎.
6. 문서 속성(docProps — 작성자 등)도 검출 대상에 들어간다.
7. 검출 세트 결함: '테스트용 계좌번호' 패턴이 전화·카드 일부도 잡는다(이중 검출). 이메일·계좌·여권·면허 패턴은 아예 없다.

### 그래서 §0-5 "지원 포맷" 의 답

**docx · xlsx · pptx · hwpx** (+ txt 기준선). PDF · HWP 는 **"지원 불가 + 사유" 로 리포트에 남긴다** —
빼지 않는다. 못 쓴다는 사실과 그 이유가 이 탭이 내야 할 결론의 절반이다.

## 3. 설계의 축 — 두 경로를 나란히 잰다

```
            ┌─ 경로 A ─ AI-R 파일 API (/air/api/detect/system/file) ─┐
문서 1건 ──┤                                                        ├─ 같은 정답으로 채점
            └─ 경로 B ─ 우리가 텍스트 추출 → AI-R 텍스트 API ────────┘
```

| A | B | 뜻 | 대응 |
|---|---|---|---|
| 됨 | 됨 | 문제 없음 | 파일 API 그대로 |
| **안 됨** | **됨** | AI-R 이 그 포맷을 **못 읽을 뿐** | **우리가 추출해 넘긴다** ← PDF · HWP 가 여기면 살릴 수 있다 |
| 안 됨 | 안 됨 | 추출은 되는데 **탐지가 못 한다** | 엔진 한계 — 제외 또는 2중 검사 |
| 됨 | 안 됨 | 우리 추출기가 더 나쁘다 | 추출기 교체 |

**PDF · HWP 가 두 번째 칸이면 그림이 바뀐다.** 지금은 "못 쓰는 포맷" 인데, 우리가 추출하면 쓸 수 있는 포맷이 된다.
이것이 경로 B 를 넣는 가장 큰 이유다.

### 추출기(경로 B) — 2026-10-18 구현·실측 완료

| 포맷 | 라이브러리 | 실측(1쪽 시험문서) |
|---|---|---|
| docx · xlsx · pptx | Apache POI 5.5.1 (`ExtractorFactory`) | 1,014자 768ms · 810자 257ms · 948자 251ms |
| **pdf** | PDFBox 3.0.3 | **538자 184ms (1쪽)** — AI-R 은 500 |
| **hwp** | hwplib 1.1.5 | **471자 91ms** — AI-R 은 500 |
| hwpx | hwpxlib 1.0.5 | 478자 273ms |
| txt | 그대로 | — |

**여섯 포맷 전부 추출되고 심은 PII 12종이 모두 추출 텍스트까지 도달했다.**
→ 기획 §3 의 두 번째 칸("AI-R 이 못 읽을 뿐")에 pdf · hwp 가 앉았다. **경로 B 로 살린다.**

구현에서 정한 것(테스트로 고정):

- **포맷은 확장자가 아니라 내용으로 판정한다** — 매직바이트 · zip 항목 · OLE 스트림 이름.
  확장자와 다르면 `extMismatch` 로 표시한다(§4.5 확장자 위조 케이스의 판정 근거).
- **글자 0자는 성공이 아니다.** 스캔 PDF 가 조용히 통과하면 비식별 안 된 문서가 '성공' 으로
  지나간다. 0자는 "OCR 필요" 라는 측정값으로 남긴다.
- `NoSuchMethodError` · `NoClassDefFoundError` 도 잡아서 결과로 돌려준다 — AI-R 이 바로
  그래서 죽었고, 예외로 날리면 측정값이 사라진다.
- **추출 단계와 검출 단계를 따로 돌려준다.** 합치면 "추출을 못 했는지" 와 "탐지를 못 했는지" 를
  가릴 수 없다. 추출이 실패하면 AI-R 을 아예 부르지 않는다 — 빈 텍스트를 보내면 검출 0건이
  탐지 실패처럼 보인다.
- 문서속성(docProps)은 본문과 **별개 파트**로 담는다. 1단계에서 거기 있던 이름이 안 가려졌는데
  한 덩어리로 합치면 어느 자리에서 남았는지 못 센다.
- PDF 는 `setSortByPosition(true)` — 표가 든 PDF 는 읽기 순서가 뒤섞인다(§4.3 과 직결).
- hwpxlib 은 `InputStream` 입구가 없다(`fromFile`/`fromFilepath` 뿐) → 임시 파일을 거친다.

> **라이브러리 버전 주의.** hwplib 은 POI 를 자기 패키지로 품고 있어(`kr.dogfoot.hwplib.org.apache.poi.*`)
> 우리 POI 와 충돌하지 않는다. 버전을 올릴 때는 AI-R 이 깨진 이유를 기억할 것 —
> 같은 라이브러리 두 벌이 한 런타임에 섞이면 `NoSuchMethodError` 로 죽는다. 우리가 그 길을 피한 이유다.

창구 — `POST /api/v1/deid/doc/extract`(추출만 · 진단) · `POST /api/v1/deid/doc/detect`(경로 B).

> **OCR 은 하지 않는다.** 이미지 PDF · 이미지 파일은 "추출 0자 → OCR 필요" 로 숫자만 남긴다.

## 4. 기능 시험 — 다섯 갈래

### 4.1 포맷 지원 매트릭스

포맷 × 경로(A · B) × {성공 · 명시적 거절 · **200 인데 빈 결과** · 타임아웃 · 5xx}.
**"200 인데 빈 결과" 를 따로 센다** — 성공처럼 보이는 실패가 가장 위험하다.

### 4.2 텍스트 변환 누락 (= 지적하신 "STT 누락")

정답 텍스트와 추출 텍스트를 맞춘다.

- `추출률` = 추출된 정답 글자 / 전체 정답 글자
- `PII 도달률` = 추출 텍스트에 살아남은 정답 PII / 심은 PII
- **자리별로 쪼갠다**: 본문 · 표 안 · 머리말/꼬리말 · 각주 · 도형 글상자 · 문서 속성 · **표 바로 뒤 문단**(hwpx 기지 결함)

PII 도달률이 100% 가 아니면 **그 차이는 비식별이 손도 못 댄 양**이다.

### 4.3 **표 구조 붕괴** — 이번 기획의 중심

> 텍스트 누락만큼 치명적인 것이 **순서 섞임**이다. 표의 주소·전화를 열 단위로 읽거나 셀이 뭉개져
> `"010-"` · `"홍길동"` · `"1234"` 가 뒤섞이면 **AI-R 이 패턴을 인식하지 못한다.**

**재는 법** — 같은 PII 를 ① 평문 문장 ② 단순 표 ③ 복잡한 표에 넣고 검출률을 비교한다.

| 표 유형 | 노리는 깨짐 |
|---|---|
| 단순 2×N | 기준(이건 돼야 한다) |
| **병합 셀**(가로 · 세로 · 교차) | 셀 경계 무너짐 |
| **셀 안 줄바꿈** | 한 값이 두 줄로 쪼개짐 — `010-1234` / `-5678` |
| **값이 여러 셀에 나뉨** | 지역번호·국번·번호가 세 칸 / 주소가 시·구·동 세 칸 |
| **여러 쪽에 걸친 표**(머리행 반복) | 쪽 경계에서 행이 끊김 |
| **중첩 표** | 표 안의 표 |
| **빈 셀 · 셀 안 표** | 열 정렬 붕괴 |
| **이름만 있는 셀**(문장 없음) | 10-08 에서 가장 많이 놓친 자리 |
| **세로쓰기 · 회전 셀** | 읽기 순서 역전 |
| 표 **바로 뒤 문단** | hwpx 기지 결함 재현 |

**판정 지표 둘**

```
셀 보존율   = 추출 텍스트에서 원래 셀 경계가 지켜진 비율
값 분절률   = 한 PII 가 둘 이상으로 쪼개져 나온 비율   ← 이게 높으면 탐지는 반드시 떨어진다
검출률 저하 = 평문 대비 − (표 유형별)
```

**값 분절률과 검출률 저하를 같은 표에 놓는다.** 상관이 보이면 "표를 어떻게 쓰면 안 되는지" 를
운영 지침으로 낼 수 있다.

### 4.4 비식별 정확도 저하 분해

```
저하분 = 평문 탐지율 − 문서 탐지율
   ├ 추출 누락 탓   (PII 도달률로 설명되는 몫)
   ├ 구조 붕괴 탓   (값 분절률로 설명되는 몫)   ← 4.3 에서 새로 생긴 축
   └ 탐지 탓        (나머지 = 엔진 한계)
```

이 분해가 없으면 "문서는 정확도가 낮다" 로 끝나고 **고칠 데를 못 찾는다.**

### 4.5 포맷 밖 · 깨진 문서 예외처리

| 입력 | 바라는 동작 |
|---|---|
| 미지원 확장자 | 명시적 거절 + 60자 이내 안내(기존 규칙) |
| **확장자 위조**(.docx 인데 PDF) | 내용으로 판정해 거절 |
| 암호 PDF · 손상 · 0바이트 | 거절 |
| 100장 · 용량 초과 | 거절 또는 분할 안내 |
| 200 + 빈 결과 | **실패로 센다** |

**어떤 경우에도 비식별 안 된 문서가 '성공' 으로 통과하면 안 된다.** 그 사건은 리포트 맨 위 위험 칸에 올린다.

## 5. 성능 시험

### 5.1 장수 임계 (최대 100장)

1 · 5 · 10 · 25 · 50 · 75 · 100 장, **장당 PII 고정**. 재는 것: 총 시간 · **장당 시간**(꺾이는 곳이 임계) ·
장수에 따른 추출률/검출률 하락(**뒤쪽 잘림**) · 실패 유형 변화.

> 10-08 기준선: 약 **1.3초/1,000자**, 15쪽 docx 약 31초. **pptx 는 슬라이드 수에 비례**해 15쪽 81초.
> → pptx 는 장수 축을 따로 그린다.

> **폴링 하한은 없다 — 확인됐다.** 파일 API(`detect/system/file`)도 동기 텍스트 API 도
> 요청 하나로 끝난다. 1초 폴링은 **그룹 텍스트 API** 경로에만 있는 항이고 여기엔 안 붙는다.

### 측정 규율 (2026-10-18 에 데여서 생긴 것)

- **예열 1회를 버린다.** 첫 호출은 JVM 예열로 10배 느리다 — 2단계에서 docx 추출이
  1,216ms → 108ms 로 떨어졌다. 예열분을 섞으면 **작은 장수가 과대평가**된다.
- **우리 쪽 벽이 먼저 오면 안 된다.** 공유 RestTemplate 읽기 20초 때문에 100장이 끊겼고,
  모르고 쟀으면 "AI-R 이 100장을 못 받는다" 로 보고할 뻔했다. 문서 경로는 별도 타임아웃
  (`deid.air.doc-read-timeout-ms`, 기본 10분)을 쓴다. 멀티파트 상한도 파일 50MB · 요청 200MB
  로 올려 뒀다 — 기본값(1MB)이면 AI-R 에 닿기도 전에 우리 쪽에서 막힌다.
- **호출이 실패하면 측정을 중단한다.** `curl -o` 는 실패 시 기존 파일을 덮지 않아
  **지난 실행 결과가 새 숫자로 읽힌다.** 실제로 한 번 그렇게 읽었다. 도구가 200 이 아니면 멈춘다.
- 회차별 값을 남기고 **중앙값**을 쓴다. AI-R 은 비결정적이다.

### 5.2 **100장 1개 vs 10장 10개** — 운영 정책의 근거

같은 100장을 **묶음 모양만 바꿔** 보낸다.

| 모양 | 파일 수 | 장/파일 | 보는 것 |
|---|---|---|---|
| 1 × 100장 | 1 | 100 | 큰 파일 한 건의 한계 |
| 2 × 50장 | 2 | 50 | |
| 4 × 25장 | 4 | 25 | |
| **10 × 10장** | 10 | 10 | 동시 요청 한계 |
| 20 × 5장 | 20 | 5 | |

**동시도**(1 · 2 · 4 · 8)와 교차한다. 재는 것: **처리량(장/분)** · **거절률** · 응답 시간 분포 ·
AI-R 쪽 큐 대기 · 실패 유형.

→ 결론을 **"첨부파일 1건 최대 n장 · 동시 최대 m건"** 한 줄로 낸다. 이것이 운영 정책 문구가 된다.

### 5.3 먹통 예외처리

| 상황 | 바라는 동작 |
|---|---|
| 응답 없음 | 타임아웃 후 **실패로 마감**(무한 대기 금지) |
| 폴링 안 끝남 | 최대 횟수에서 끊고 사유 기록 |
| 일부만 처리 | **부분 성공** — 어디까지 됐는지 장 번호로 |
| 5xx · 연결 끊김 | 재시도 횟수·간격 기록 후 실패 |
| 시험 중단 | [중단] — 지금까지 결과 보존 |

### 5.4 운영 환산

채팅 20초 요구에 몇 장까지 들어가는가 · 100장은 몇 분인가. 병렬도는 가정하지 않고 **필요 배수**만 낸다.

## 11. 시험 문서는 어떻게 만드는가 (2026-10-18 실측으로 확정)

§0-6 — "시험 문서는 파일로 만들어 채팅 실화면에서도 쓴다" 를 실제로 만들어 보고 정리했다.

### 11.1 포맷별 생성 수단

| 포맷 | 생성 수단 | 서버(쿠버네티스)에서 되는가 |
|---|---|---|
| docx | python-docx / Apache POI | **된다** |
| xlsx | openpyxl / POI | **된다** |
| pptx | python-pptx / POI | **된다** |
| **hwp · hwpx** | **한글 COM**(`HWPFrame.HwpObject`) | **안 된다** — 한글이 깔린 PC 에서만 |
| **pdf** | 한글 COM 내보내기(또는 PDF 라이브러리) | 한글로는 안 된다. 라이브러리 필요 |

**이것이 설계를 바꾼다.** hwp · hwpx 시험 문서는 **클러스터에서 만들 수 없다.**
→ 한글이 깔린 PC 에서 미리 만들어 **레포에 담아 둔다**(고정 자산). docx · xlsx · pptx 는 조건
(장수 · 표 유형 · PII)별로 **그때그때 생성**한다. 화면의 [문서 만들기] 는 이 두 갈래를 섞어 내려준다.

> 10-18 확인: 이 PC 에 한글 13(2024)이 있고 COM 이 동작한다. Word 는 **없다**(ProgID 는 남아 있지만
> 클래스 미등록 — `REGDB_E_CLASSNOTREG`). 그래서 pdf 도 한글 내보내기로 만들었다.

### 11.2 새로 찾은 시험 케이스 — 한글이 XML 수치참조로 들어간다

openpyxl 로 만든 xlsx 는 한글을 그대로 쓰지 않고 **XML 수치참조**(`홍길동` → `&#54861;&#44600;&#46041;`)로 쓴다.
XML 로서는 정상이고 제대로 된 파서(POI)는 풀어서 읽는다. 하지만 **XML 을 정규식으로 긁는 구현이라면
한글을 아예 못 본다.**

→ **시험 케이스로 넣는다.** 같은 내용을 ① 평문 그대로 ② 수치참조로 쓴 두 벌을 만들어 결과를 비교한다.
차이가 나면 AI-R 의 추출이 파서가 아니라 문자열 처리라는 뜻이고, 그건 포맷 지원 여부보다 큰 문제다.

(내 검사기가 먼저 이 함정에 걸렸다 — 수치참조를 안 풀어서 xlsx 를 "PII 4건 누락" 으로 잘못 읽었다.
문서를 고칠 뻔했다. 채점기는 반드시 엔티티를 풀고 비교해야 한다.)

### 11.3 1단계 탐침 문서 (실제로 만든 것)

한 벌(`deid_probe.*`)을 6포맷으로 만들었다 — 내용과 정답이 **포맷 간 동일**해야 포맷 탓과 내용 탓이 안 섞인다.

- 심은 PII 10종: 이름 3 · 휴대전화 · 유선전화 · 주민번호 · 계좌 · 주소 · 기관 · 이메일
- 자리 9곳: 본문 3 · 표(단순 · 값분할 · 셀내줄바꿈 · 병합+이름만) · **표 바로 뒤 문단** · 머리말 · 꼬리말 · 문서속성
- 표 케이스 4종을 **1쪽 안에** 넣었다 — 1단계에서도 §4.3 지표를 같이 잴 수 있다
- `answers.json` 을 같이 낸다(자리 · 종류 · 값) → 채팅 실화면 시험도 같은 정답으로 채점

docx 10/10 · xlsx 10/10 · pptx 10/10 · hwpx 10/10 로 PII 가 살아 들어간 것을 확인했다
(pdf · hwp 는 바이너리라 문자열 검사 대신 AI-R 결과로 확인한다).

`010-9876-5432` 는 **일부러** docx XML 문자열 검사에 안 걸린다 — 셀 안에서 두 줄로 끊어 둔 값이라
런(run)이 쪼개져 있다. 이게 §4.3 '값 분절' 케이스의 실체다.

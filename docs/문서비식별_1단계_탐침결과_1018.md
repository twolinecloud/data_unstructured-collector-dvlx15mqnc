## 2. 포맷보다 큰 구멍 — 검출 세트

### 2.1 주민등록번호 — 패턴은 있다. **체크섬을 검사한다**

`900101-1234567` 이 네 포맷 전부에서 안 가려졌다. 세트를 열어 보니 패턴은 **3개가 다 있었다.**

| 규칙 id | 무엇을 잡나 |
|---|---|
| `6a78df5a…` | **주민등록번호** |
| `1a53a8ac…` | 휴대전화 · 유선전화 |
| `d9b56777…` | 계좌, 그리고 **전화번호까지** (기지 이중검출) |

그래서 텍스트 API 로 꼴을 바꿔 가며 직접 쟀다.

| 입력 | 결과 |
|---|---|
| `900101-1234568` (체크섬 **맞음**) | **잡힌다** → `**************` |
| `900101-1234569` (체크섬 틀림) | 안 잡힌다 |
| `900101-1234567` (내가 쓴 값 — 체크섬 틀림) | 안 잡힌다 |
| `9001011234568` (체크섬 맞음, **하이픈 없음**) | **안 잡힌다** |
| `주민등록번호는 900101-1234568 입니다` | 잡힌다 |
| `주민등록번호는 900101-1234567 입니다` | 안 잡힌다(문맥 무관) |

**둘이 나왔다.**

**① 측정 함정 — 내 시험 데이터가 틀렸다.**
가상 주민번호를 체크섬 안 맞춰 만들면 **영원히 미탐으로 보인다.** 그 상태로 보고하면
"AI-R 이 주민번호를 못 잡는다" 는 틀린 결론이 나간다. 포맷 탓도 아니고 엔진 탓도 아니고
**시험 데이터 탓**이었다. → 시험 문서 생성기는 주민번호를 **체크섬을 맞춰** 만들어야 한다.
(함정을 기록하기 위해 체크섬 틀린 값도 한 건 같이 심는다.)

**② 진짜 구멍 — 하이픈 없는 13자리는 체크섬이 맞아도 안 잡힌다.**
`9001011234568`. 실문서에서 드물지 않은 꼴이다(엑셀 셀, 표 입력, 붙여쓰기).
이건 시험 데이터 문제가 아니라 **패턴 자체의 한계**다. 정규식은 형식 식별자를
100% 잡을 수 있는 수단인데, 지금 세트는 하이픈 있는 꼴만 본다.

> 교훈이 하나 더 있다. **"미탐" 을 보면 먼저 시험 데이터를 의심해야 한다.**
> 네 포맷이 모두 똑같이 못 잡으면 그건 포맷의 성질이 아니다.

### 2.2 이메일 · 주소 · 기관은 '맞는 이유로' 가려진 게 아니다

| 값 | 결과 | 무엇으로 잡혔나 |
|---|---|---|
| `hong.gildong@example.com` | 가려짐 | **SS_NAME**(이름) — 이메일 패턴은 세트에 없다 |
| `서울특별시 강남구 테헤란로 123` | 가려짐 | AD_ADDRESS · AD_CITY · AD_METRO 가 **조각으로** 걸침 |
| `서울남부교정시설` | 가려짐 | AD_METRO · ORG_DEPT · ORG_NPO 가 걸침 |

가려지긴 했다. 하지만 **값 전체를 하나의 개체로 잡은 게 아니라 조각이 겹쳐 덮인 것**이다.
조각이 하나라도 안 걸리면 부분 노출이 된다 — 실제로 본문 이메일은
`*********ong@example.com` 처럼 **뒤쪽이 남았다**.

## 3. 이름 — 문맥 없는 자리에서 무너진다

가장 선명한 결과다.

| 값 | docx | xlsx | pptx | hwpx |
|---|---|---|---|---|
| 홍길동 | 5회 중 **2회 남음** | 0 | 3회 중 **3회 남음** | 3회 중 **3회 남음** |
| 김영희 | 0 | 0 | 0 | 0 |
| 박철수 | 0 | 0 | 0 | 0 |

docx 파트별로 보면 어디서 남는지가 분명하다.

| 파트 | 내용 | 남은 평문 |
|---|---|---|
| 0 (21자) | `홍길동 연락처 010-1234-5678` (문서속성) | **홍길동** |
| 1 (448자) | 본문·표 전체 | 900101-1234567 |
| 2 (14자) | `머리말 — 작성자 홍길동` | **홍길동** |
| 3 (23자) | `꼬리말 — 문의 010-1234-5678` | 없음 |

**같은 파트에서 전화번호는 가려지고 이름만 남았다.** 정규식은 조각이 짧아도 돌고,
딥러닝 이름 인식은 **문맥이 없으면 안 돈다.** 머리말 · 꼬리말 · 문서속성 · 표 셀이
전부 그 꼴이다.

> 이것이 10-08 에 "남은 건 대부분 표의 이름 칸" 으로 관측된 것의 정체다.
> 표라서가 아니라 **문맥이 없어서**다. 머리말에서도 똑같이 남는다.
>
> 가름이 노리는 축과 정확히 겹친다 — 가름은 문맥 없는 자리의 이름을
> 성씨 사전 · 형태소 · 문서 전파로 집어내는 쪽이다. 문서 비식별에
> 가름을 얹을 근거가 여기서 처음 실측으로 나왔다.

pptx · hwpx 에서 홍길동이 **0건 검출**인 이유도 같다 — 그 문서에서 홍길동이 들어간
자리가 제목 · 표 셀 · 문서속성뿐이고, 본문 문장에는 김영희 · 박철수만 있었다.

## 4. 표 구조 — 1쪽 규모에서는 안 깨졌다

| 케이스 | 결과 |
|---|---|
| 단순 2열 | 추출 · 검출 모두 정상 |
| 값 분할(`010`/`1234`/`5678` 세 칸) | docx · hwpx 는 **줄 단위로 분리**, xlsx 는 **공백으로 이어짐** |
| 셀 안 줄바꿈(`010-` ⏎ `9876-5432`) | **줄바꿈 그대로 남는다** → 전화 패턴이 안 맞는다 |
| 병합 + 이름만 있는 칸 | 추출 정상, 이름 검출은 §3 그대로 |
| 표 바로 뒤 문단(hwpx 기지 결함) | **이 규모에서는 재현되지 않았다** |

분절된 `9876-5432` 는 마스킹 결과에 **남지 않았다** — `d9b56777…`(계좌/전화 겸용 패턴)이
조각을 주워 덮었다. 운 좋게 덮인 것이고, 세 칸으로 나눈 `010 1234 5678` 은 아무것도
안 걸렸다. **표에 값을 쪼개 넣으면 탐지가 떨어진다**는 방향은 확인됐지만, 숫자로
확정하려면 3단계의 복잡한 표 · 여러 쪽 표가 필요하다.

## 5. 측정에서 걸린 함정 (3단계 설계에 반영할 것)

### 5.1 변환으로 만든 문서는 포맷 간 비교가 안 된다

docx 를 한글로 열어 hwpx · pdf · hwp 로 저장했는데, **심은 PII 출현 횟수가 달라졌다**
(docx 20회 · hwpx 16회). 머리말 · 문서속성 일부가 변환에서 사라진 것이다.
AI-R 탓이 아니고 **한글 변환 탓**이다.

→ 포맷을 정면으로 비교하려면 **각 포맷을 직접 생성**해야 한다(hwpx 는 OWPML 을 직접 쓴다).
변환본으로는 "그 포맷이 되는가" 까지만 말할 수 있다.

### 5.2 한글이 XML 수치참조로 들어간다

openpyxl 로 만든 xlsx 는 `홍길동` 을 `&#54861;&#44600;&#46041;` 로 쓴다. XML 로서는
정상이고 POI 는 풀어 읽는다. **내 검사기가 먼저 이 함정에 걸려** xlsx 를
"PII 4건 누락" 으로 잘못 읽었다. 채점기는 반드시 엔티티를 풀고 비교해야 한다.

→ 거꾸로 **시험 케이스로 쓸 값**이 있다. 같은 내용을 평문 / 수치참조 두 벌로 만들어
결과가 다르면, AI-R 의 추출이 파서가 아니라 문자열 처리라는 뜻이다.

### 5.3 자리별 O/X 는 전체 검색으로 만들 수 없다

처음 채점에서 "홍길동 5자리 전부 미가림" 으로 찍혔는데, 실제로는 5회 중 2회였다.
전체 마스킹 텍스트에서 값을 찾으면 **한 군데만 남아도 모든 자리가 X** 가 된다.
→ **출현 횟수**(원문 n회 / 잔존 m회)와 **파트별**로 세는 것이 맞다. 리포트도 그렇게 짠다.

### 5.4 AI-R 은 스펙을 노출하지 않는다

`/air/v3/api-docs` · `/air/v2/api-docs` · `/air/swagger-resources` · `/v3/api-docs`
**전부 404**. 파일 API 의 멀티파트 계약은 **오류 메시지로** 알아냈다 —
`MissingServletRequestParameterException: Required request parameter 'data'`.

확정된 계약: **`file`**(파일 파트) + **`data`**(검출 요청 JSON 문자열 파트).
커넥터 기본값에 박았고, 서버 판이 바뀌면 화면에서 바꿔 끼울 수 있게 파라미터로도 남겼다.

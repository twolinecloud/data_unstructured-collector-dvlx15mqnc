## 한 줄 결론

**경로 B 가 성립한다.** AI-R 이 HTTP 500 으로 거절하는 pdf · hwp 를 우리는 각각
**184ms · 91ms** 에 열고, 심은 개인정보 12종이 **전부 추출 텍스트까지 도달**한다.
→ 기획 §3 의 두 번째 칸("AI-R 이 그 포맷을 못 읽을 뿐")에 pdf · hwp 가 앉았다. **살릴 수 있다.**

다만 조건이 하나 붙는다 — **PDF 의 표는 추출 설정에 따라 값이 쪼개진다**(§5). 그 설정을 바로잡아야 쓸 수 있다.

## 2. 중간에 한 번 잘못 읽었다 — 기록해 둔다

처음 추출 결과는 docx **1,014자**였다. AI-R 파일 API 가 같은 문서에서 509자를 뽑았으니
"우리가 두 배 더 뽑는다" 로 읽었다. **틀렸다.**

문서의 실제 내용을 자리별로 세 보니 **539자**였다(본문 368 · 표 셀 116 · 머리말 13 ·
꼬리말 22 · 문서속성 20). 1,014자는 더 뽑은 게 아니라 **군더더기가 붙은 것**이었다 —
POI 메타데이터 추출기가 속성을 전부 덤프해서, 문서속성 파트 493자 중
**개인정보는 20자, 나머지 473자가 `Application = Microsoft Office Word` 류**였다.

그대로 넘기면 두 가지를 잃는다.

| 잃는 것 | 왜 |
|---|---|
| **시간** | AI-R 검출은 글자수에 비례한다(약 1.3초/1,000자). 군더더기가 호출 시간을 몇 배로 늘린다 |
| **정확도** | 제품명 · 회사명 · 템플릿 이름이 기관 라벨로 잡혀 **오탐**이 된다 |

그래서 **사람이 들어갈 수 있는 칸만** 남겼다(author · creator · lastModifiedBy · manager ·
company · comments · description · title · subject · keywords · category).
키 이름은 같이 남긴다 — `Author = 홍길동` 의 "Author" 가 딥러닝에 문맥을 준다.
**1단계에서 확인했듯 이름은 문맥이 없으면 안 잡힌다.**

결과: docx 1,014 → **567자**, xlsx 810 → 423, pptx 948 → 476. **PII 도달은 그대로 12/12.**

> 교훈 — **합계만 보면 "더 뽑았다" 와 "군더더기가 붙었다" 를 못 가린다.**
> 그래서 테스트가 파트별 글자수를 같이 낸다. 못 가려서 한 번 잘못 읽었다.

## 3. 설계에서 정한 것 (테스트로 고정)

| 결정 | 왜 |
|---|---|
| **포맷은 확장자가 아니라 내용으로 판정** — 매직바이트 · zip 항목 · OLE 스트림 이름 | 확장자 위조가 시험 항목이다. 불일치는 `extMismatch` 로 표시 |
| **글자 0자는 성공이 아니다** | 스캔 PDF 가 조용히 통과하면 **비식별 안 된 문서가 '성공' 으로 지나간다**. 0자는 "OCR 필요" 라는 측정값 |
| `NoSuchMethodError` · `NoClassDefFoundError` 도 잡아 결과로 돌려준다 | AI-R 이 바로 그래서 죽었다. 예외로 날리면 측정값이 사라진다 |
| **추출 단계와 검출 단계를 따로** 돌려준다 | 합치면 "추출을 못 했는지" 와 "탐지를 못 했는지" 를 못 가린다 |
| 추출 실패 시 **AI-R 을 아예 부르지 않는다** | 빈 텍스트를 보내면 검출 0건이 탐지 실패처럼 보인다 |
| 문서속성은 본문과 **별개 파트** | 1단계에서 거기 있던 이름이 안 가려졌다. 합치면 어느 자리에서 남았는지 못 센다 |
| PDF 는 `setSortByPosition(true)` | 표가 든 PDF 는 읽기 순서가 뒤섞인다(§4.3 표 구조와 직결) |

hwpxlib 은 `InputStream` 입구가 없어(`fromFile`/`fromFilepath` 뿐) 임시 파일을 거친다.

### 라이브러리 충돌을 피한 방법

AI-R 이 깨진 이유가 바로 **같은 라이브러리 두 벌이 한 런타임에 섞인 것**이다
(pdfbox 3.x 코드 + 2.x 런타임 → `NoSuchMethodError`). 우리는 그 길을 피했다.

- `hwplib` 은 POI 를 **자기 패키지로 품고** 있다(`kr.dogfoot.hwplib.org.apache.poi.*`)
  → 우리 POI 5.5.1 과 충돌하지 않는다
- pdfbox 는 3.0.3 한 벌만 올린다
- **버전을 올릴 때 이 문서를 볼 것.** 같은 사고를 우리가 낼 수 있다

## 5. PDF 에서 표가 깨졌다 — 범인은 우리 설정이었다

기획 §4.3 이 걱정한 **값 분절**("표 안 전화번호를 열 단위로 읽거나 셀이 뭉개져
`010-`, `홍길동`, `1234` 가 뒤섞이면 AI-R 이 패턴을 인식하지 못한다")이
PDF 경로에서 **그대로 재현**됐다. 그런데 원인이 AI-R 도 PDFBox 도 아니고 **우리 설정**이었다.

처음엔 "표가 든 PDF 는 읽기 순서가 뒤섞인다" 고 `setSortByPosition(true)` 를 켰다.
같은 파일로 둘 다 재 보니 **켠 쪽이 표를 부쉈다.**

| 자리 | 좌표 정렬 **ON** | 좌표 정렬 **OFF** |
|---|---|---|
| 값 분할 표(`010`/`1234`/`5678` 세 칸) | `지01역0 국12번34 번56호` — 헤더와 값이 **글자 단위 교차** | `지역 국번 번호010 1234 5678` — 분리 |
| 셀 안 줄바꿈(`010-` ⏎ `9876-5432`) | `연락처 091807-` … `표4. 병합 + 6-5432` — **조각남** | `연락처 010-9876-5432` — **한 값** |
| 표 뒤 문단 | `02-3456-789지0인` — 옆 셀 "지인" 이 전화번호에 끼어듦 | `연락처 02-3456-7890` — 온전 |
| 주소 | `주` … `표2소.` — 두 글자가 다른 줄로 | 온전 |

**왜** — 좌표 정렬은 y 가 비슷한 글자를 한 줄로 모은다. 표에서는 **두 행이 거의 같은 y** 라
서로 섞인다. 끄면 문서 순서(그리는 순서)로 읽고, 표는 보통 셀 단위로 그려지므로 값이 온전하다.

**끄기로 했다.** 읽기 순서가 덜 자연스러운 것(꼬리말이 앞에 오고 표 제목이 셀보다 먼저)보다
**값이 쪼개지는 것이 훨씬 치명적**이다.

- 형식 식별자(전화 · 주민 · 계좌)는 정규식이라 **순서와 무관**하다. 값이 붙어 있어야만 맞는다
- 이름은 문맥이 필요한데, 1단계에서 이미 **문맥 없는 자리에서는 못 잡힌다**는 게 드러났다.
  순서를 지켜 줘도 그 자리는 어차피 안 된다

`PdfTableOrderTest` 가 둘을 나란히 출력하고, 고른 쪽을 못 박는다 —
**셀 안에서 줄바꿈된 전화번호가 한 값으로 나와야 한다.**

> 이 발견의 값은 따로 있다. **표 구조 붕괴는 엔진 탓만이 아니다.** 추출 단계의 설정
> 하나로 탐지 가능/불가능이 갈린다. 3단계에서 복잡한 표를 잴 때, 숫자가 나쁘면
> 엔진을 의심하기 전에 **추출 설정을 먼저 본다.**

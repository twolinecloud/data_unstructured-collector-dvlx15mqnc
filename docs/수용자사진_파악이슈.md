## 이슈 1. 순번이 뒤인데 촬영(생성)일이 더 이른 사진

- 개발계: 사진이 여러 장인 수용자의 순번 쌍 810개 중 **61개**가 "순번은 뒤 · `CRT_DT` 는 앞".
- 정정 입력 · 데이터 이관 · 마스킹 영향 같은 **비정상 데이터일 수 있어** 무조건 촬영일을 따르는 것이 맞다고 볼 수 없다.
- 지금 동작: 순번 최대를 대표로 쓴다. 매핑은 "기존 순번 ≤ 새 순번" 일 때만 덮는다(늦게 끝난 옛 사진이 새 사진을 덮지 않게).
- **바꿀 때 주의**: 대상 선택만 `CRT_DT` 로 바꾸면 순번이 더 작은 '촬영일 최신' 사진이 덮어쓰기 막기에 걸려 **영영 반영되지 않는다** —
  대상 선택(`CRT_DT DESC, IMAGE_SN DESC`)과 덮어쓰기 규칙("원천의 지금 대표와 다르면 교체")을 **같이** 바꿔야 한다
  (`ImageSourceService.queryLatest` · `ImageCollectService.processOne` · `InmatePhotoRepository` upsert).
- 판단 시점: 운영 데이터에서 아래 SQL 로 건수를 보고, 실제로 있으면 보라미 담당께 그 사진들이 정상인지 확인한 뒤 정한다.

```sql
-- 순번은 뒤인데 생성일이 앞선 사진 쌍(화상이미지)
SELECT count(*) AS pairs,
       count(*) FILTER (WHERE b.crt_dt < a.crt_dt) AS sn_up_date_down
  FROM ir.tb_irim_bsif_ds a
  JOIN ir.tb_irim_bsif_ds b ON a.corr_no = b.corr_no AND b.image_sn > a.image_sn
 WHERE a.image_se_cd = '1' AND b.image_se_cd = '1';
```

## 이슈 2. 보라미에서 사진을 지우면

- `TB_IRIM_BSIF_DS` 에는 **삭제 표시 컬럼이 없다**(`CRT_DT` · `MDFCN_DT` 만) — 삭제는 물리 삭제이고, 언제 지워졌는지 알 수 없다.
- 정형 수집기도 같다: 소프트 삭제(`DEL_YN` 등 원천 표시)는 증분 스캔이 '삭제(D)' 로 반영하지만,
  **표시 없는 테이블의 물리 삭제는 "감지 불가 — 범위 밖(보라미 이슈)"** 로 두었다(`DeleteFlags` · `AuditScanDeltaSource`).
  정형은 이 사진 테이블도 순번 단위 항목으로 수집하므로, 지워진 사진 항목이 **정형 피처 문서에도 남는다**.
- 지금 동작:

| 경우 | 결과 |
|---|---|
| 최신이 아닌 사진 삭제 | 영향 없음 |
| **최신 사진 삭제**(예: 순번 3 삭제 → 진짜 최신은 2) | 덮어쓰기 막기가 순번 2 를 옛 사진으로 막아 **지워진 순번 3 이 계속 대표로 남는다** |
| 사진 전부 삭제 | 원천 조회에 나오지 않아 **매핑이 그대로 남는다** |

- 개발계: 순번에 빈칸이 있는 수용자 377/1000, 1 부터 시작하지 않는 수용자 337 — 실제 삭제인지 개발계용 일부 복사 때문인지는 구분할 수 없다.

### 생기면 대응(수동)

`force=true` 로도 풀리지 않는다(강제는 '변경 없음' 건너뛰기만 푼다 — 더 최신 순번이 매핑돼 있으면 여전히 덮지 않는다).

1. Admin DB 매핑에서 그 수용자를 지운다 — `DELETE FROM kcais.tb_src_inmate_photo WHERE corr_no = '…';`
2. 그 수용자만 다시 수집한다 — `POST /api/v1/image/batches` `{"corrNos":["…"]}` → 원천의 지금 최신 사진으로 다시 매핑(사진이 하나도 없으면 매핑 없음으로 끝)
3. 지워진 사진의 저장 파일(`{IMAGE_OUTPUT_DIR}/{CORR_NO}/…`)은 남으니 필요하면 지운다

긴급 재처리 대상은 아니다 — 삭제는 실패가 아니라 원천이 바뀐 것이다.

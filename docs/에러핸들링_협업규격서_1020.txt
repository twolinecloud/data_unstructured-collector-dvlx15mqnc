[0] 먼저 합의할 것 — 상태 코드 약속 4개
--------------------------------------------------------------------
화면이 이 넷만 구분하면 됩니다. 지금은 전부 "일시적인 네트워크 문제"
한 문구로 보여 사용자가 원인을 알 수 없습니다.

  4xx   하위가 밝힌 업무 사유       → 백엔드 message 를 그대로 노출
  504   응답 지연 · 시간 초과       → "처리 중일 수 있음" + 버튼 60초 잠금
        (※ 중요: 요청이 들어갔을 수 있으므로 재시도를 유도하면 안 됩니다)
  503   하위 미설정 · 연결 실패     → "잠시 후 다시 시도" (처리 안 됨이 확실)
  500   admin-api 자체 오류          → "서버 내부 오류"

타임아웃 사슬 — 안쪽이 먼저 끊겨야 합니다.
  커넥터 read 60s  <  admin-api 비동기 70s  <  nginx /api/ 75s  <  화면 80s
  지금은 admin-api 비동기 타임아웃이 없어 Tomcat 기본 30초가 먼저 걸리고,
  nginx /api/ 도 기본 60초라 순서가 뒤집혀 있습니다.

 PART A.  admin-api 담당자

A-1. 지금 코드가 뒤바뀌어 나가는 API (고칠 대상)
--------------------------------------------------------------------
아래 다섯 건은 하위 서비스가 정확한 코드를 주는데 admin-api 에서 바뀝니다.

증상 확인 화면 (개발계 https://kcais-admin.twolinecloud.com)
  [스케줄]  파이프라인 운영 > 배치 스케줄 설정   /pipeline/batch-schedule
            → 행의 [바로 실행] → 팝업 [바로 실행]
  [목록]    파이프라인 운영 > 배치 수행 이력     /pipeline/batch-history
            → 행의 [긴급 재처리] → 팝업 [재처리]
            (실패·부분성공·취소·전송 대기 등 재처리 가능한 행에만 버튼이 있습니다)
  [모달]    같은 화면에서 실행 ID 클릭 → 배치 상세 모달 하단 [긴급 재처리] → [재처리]
  [대시보드] 대시보드 /dashboard → "데이터 유형별 마지막 실행 결과" 카드의
            [긴급 재처리] → 팝업 [재처리]  (같은 재처리 API · 실패 시
            "재처리 요청 실패 / 상태코드 고정 문구")
  [바쁘게]  "수집기 실행 중" 만들기 — 비정형 시뮬레이터
            https://kcais-admin.twolinecloud.com/unstructured_collector_simulator.html
            → 6. 수용자 이미지 수집 검증 탭 → "가상 처리 지연(ms)" 을 크게 잡아 실행
            (도는 동안 수집기는 바로 실행 · 재처리를 "실행 중" 으로 거절합니다.
             2번 탭 음성 배치 버튼으로도 되지만 금방 끝날 수 있습니다)
  ※ 화면 문구는 admin-fe 상태코드 고정 문구라 코드 차이는 브라우저
    개발자도구 Network 탭의 상태 코드 · 응답 본문으로 보는 것이 확실합니다.

 [ ] A-1-1  POST /api/batch-schedules/{dataTypeCd}/run
            지금: 수집기 409(실행 중) → 400 으로 변환
            필요: 409 그대로
            이유: 화면이 "잠시 뒤 다시"와 "입력을 고쳐 다시"를 못 가릅니다
            위치: BatchRunClient (하위 상태코드를 Result 에 담고 있지 않음)
            화면: [스케줄] [바로 실행]
            재현: 지금 개발계 RUN_URL(/internal/collect/*)은 정형 · 비정형 모두
                  실행 중일 때 409 가 아니라 200 accepted:false 를 줍니다
                  → 이 증상 대신 A-1-2 로 나타납니다. RUN_URL 이 409 를 주는
                  경로(예: 비정형 /api/v1/admin/batch/run)일 때만 보입니다
            보이는 것: "바로 실행 실패 / 요청이 올바르지 않습니다." (Network 400)

 [ ] A-1-2  POST /api/batch-schedules/{dataTypeCd}/run
            지금: 수집기가 200 {result:{accepted:false, reason:"이미 실행 중"}}
                  로 거절했는데 성공(REQUESTED, execId=null)으로 처리
            필요: 409 + reason 을 message 로
            이유: 화면에 "바로 실행 완료"가 떠 거짓 성공입니다 (가장 시급)
            대상 경로: /internal/collect/unstructured-incremental (RUN_URL)
            화면: [스케줄] 비정형 행 [바로 실행]
            재현: [바쁘게] 로 수집기를 돌려 둔 채 [바로 실행]
                  (또는 [바로 실행] 을 연달아 두 번)
            보이는 것: "비정형 바로 실행 완료" 성공 토스트. 그런데 [목록] 에
                  새 실행 이력이 생기지 않습니다 (Network 200, execId null)

 [ ] A-1-3  POST /api/batch-exec-logs/{execId}/reprocess
            지금: 수집기 409 → 400
            필요: 409 그대로
            화면: [목록] [긴급 재처리] · [모달] [긴급 재처리] · [대시보드] [긴급 재처리]
            재현: [바쁘게] 로 수집기를 돌려 둔 채 비정형 행 재처리
            보이는 것: [목록] "재처리 실행 실패 / 일시적인 네트워크 문제가
                  발생했습니다."  [모달] "재처리 요청 실패 / 요청이 올바르지
                  않습니다."  [대시보드] "재처리 요청 실패 / 요청이 올바르지
                  않습니다."  (Network 400 — 수집기는 409 를 줬습니다)

 [ ] A-1-4  POST /api/batch-exec-logs/{execId}/reprocess
            지금: message 없는 4xx(경로 오류 404 등)도 503
            필요: 상태코드 보존. message 가 없으면 A-2 의 기본 문구 사용
            화면: [목록] [긴급 재처리] · [모달] [긴급 재처리] · [대시보드] [긴급 재처리]
            재현: 수집기의 4xx 는 늘 message 가 있어 화면 조작만으로는 안 납니다.
                  재처리 URL 설정을 없는 경로로 바꿔야 404 가 납니다
                  (개발계 DB 수정이 필요하니 admin-api 로컬에서 확인 권장)
            보이는 것: [목록] "일시적인 네트워크 문제…"  [모달] "서버 오류가
                  발생했습니다…"  (Network 503 — 수집기는 404 를 줬습니다)

 [ ] A-1-5  수집기 호출 read 타임아웃 3초
            지금: 3초 초과와 수집기 5xx·연결 실패가 모두 같은 503
            필요: 타임아웃은 504(처리 중일 수 있음), 연결 실패·5xx 는 503
            이유: 재처리는 수집기가 로그 컬렉터를 2회 동기 조회하고 execId 를
                  1.5초 기다린 뒤 202 를 줍니다. 3초를 넘기면
                  "접수됐는데 503" 이 됩니다
            화면: [목록] [긴급 재처리] · [모달] [긴급 재처리] · [대시보드] [긴급 재처리] ·
                  [스케줄] [바로 실행] (같은 3초 클라이언트를 씁니다)
            재현: 수집기 · 로그 컬렉터가 느릴 때만 나서 일부러 만들기 어렵습니다.
                  수집기 파드를 내려 두면 "연결 실패 503" 쪽은 볼 수 있습니다
            보이는 것: 실패 토스트(Network 503)가 떴는데, 몇 초 뒤 [목록] 을
                  새로고침하면 그 재처리 · 실행 이력이 생겨 있습니다
                  → 이것이 "접수됐는데 503" 입니다


A-2. API 별 한글 안내 문구 (공백 포함 50자 이내 · 2줄 이하)
--------------------------------------------------------------------
지금 admin-api 자체 4xx/5xx 문구가 영문 개발자 메시지입니다
("batch exec log not found: …", "agent-connector request failed").
admin-fe 가 message 를 그대로 띄우기 시작하면 영문이 화면에 노출됩니다.

  API / 상황                                   → 내려줄 message (자수)
  ---------------------------------------------------------------
  cloud-sends/{id}/release · DB 에 배치 없음
      "선택한 배치를 찾을 수 없습니다. 목록을 새로고침해 주세요."   (32)
  cloud-sends/{id}/release · 정형·비정형 아님
      "클라우드 전송은 정형 · 비정형 배치만 가능합니다."            (28)
  cloud-sends/{id}/release · 커넥터 연결 실패·미설정·5xx
      "에이전트 커넥터를 호출하지 못했습니다. 잠시 후 다시 시도해 주세요." (41)
  cloud-sends/{id}/release · 커넥터 응답 지연(504)
      "응답이 늦습니다. 처리 중일 수 있으니 새로고침해 확인해 주세요."  (36)
  batch-schedules/{type}/run · 이미 실행 중(409)
      "이미 실행 중인 배치입니다. 잠시 후 다시 시도해 주세요."       (31)
  batch-exec-logs/{id}/reprocess · 수집기 4xx 인데 message 없음
      "재처리를 시작하지 못했습니다. 잠시 후 다시 시도해 주세요."    (33)
  공통 · admin-api 내부 오류(500)
      "서버 내부 오류가 발생했습니다. 잠시 후 다시 시도해 주세요."   (33)

  ※ 하위(커넥터·수집기)가 이미 한글 message 를 준 경우에는
     위 문구로 덮어쓰지 말고 그대로 전달하십시오(A-3).
  ※ 자수 기준: 화면 15px · 글자 영역 330px 에서 한글은 약 54자부터
     3줄이 됩니다. 50자 이하면 2줄 안에 들어갑니다.


A-3. 왜곡 없이 바이패스해야 할 대상 (하위 message · 상태코드 보존)
--------------------------------------------------------------------
아래는 하위 서비스가 이미 화면용 한글 문구를 만들어 보냅니다.
admin-api 는 상태코드와 message 를 **그대로** 올려 주시면 됩니다.

 [ ] POST /api/cloud-sends/{execId}/release
       ← 커넥터 404 "보류 중인 전송이 없습니다 — {execId}"
       ← 커넥터 409 "지금 전송 중입니다 — {execId}"
       ← 커넥터 200 {success:false, message:"[PPP] …"}  ← 본문 그대로
       (현재 relay() 가 이미 잘 하고 있습니다. 유지해 주십시오)

 [ ] POST /api/cloud-sends/{execId}/stop
       ← 커넥터 200 {accepted:false}
       필요: 409 로 올리고 message "중지할 수 있는 전송이 없습니다." (23)
       참고: 음성(LEARN 경로)은 실제 전송 중이어도 늘 accepted:false 입니다.
             커넥터 중지는 추론(정형) 워커만 대상이라 구조가 그렇습니다.
             → 비정형 행에서는 [클라우드 전송 중지] 를 숨기는 것도 방법입니다

 [ ] POST /api/batch-schedules/{dataTypeCd}/run
       ← 수집기 400 (60자 이내 한글 안내. 예: "최근 수집 시점(…) 이후의
         시간을 선택해 주세요. 과거 구간은 '긴급 재처리'를 이용 바랍니다.")
       (현재 전달은 되고 있습니다 — 화면에서 버려지는 것이 문제입니다. PART B)

 [ ] POST /api/batch-exec-logs/{execId}/reprocess
       ← 수집기 400/409 한글 안내


A-4. 504 전환 — 비동기 타임아웃 70초
--------------------------------------------------------------------
 [ ] 비동기(Callable) 타임아웃을 70초로 설정
       지금 미설정이라 Tomcat 기본 30초가 먼저 걸리고, catch-all 500 이 나갑니다.
       설계상 의도한 "60초 넘으면 진행 중일 수 있음" 응답이 실제로는 안 나옵니다.

 [ ] 타임아웃 시 504 로 응답
       본문 규격:
         HTTP/1.1 504
         { "error": true,
           "http_status_code": 504,
           "message": "응답이 늦습니다. 처리 중일 수 있으니 새로고침해 확인해 주세요." }

 [ ] catch-all 500 본문의 http_status_code 를 500 으로
       지금 공통 ErrorResponse 기본 생성자가 503 을 넣어 상태 줄과 본문이
       어긋납니다. 본문을 믿는 소비자가 500 을 503 으로 오판합니다.
       (커넥터는 2026-10-20 에 이 건을 고쳐 500 으로 내보냅니다 — PART C 실측)

 [ ] 500 응답에도 message 키를 넣어 주십시오
       커넥터 INTERNAL_ERROR 실측 본문에 message 가 없습니다(PART C).
       admin-api 도 같은 템플릿이면 같은 증상입니다.


====================================================================
 PART B.  admin-fe 담당자
====================================================================

B-1. 공통 인터셉터 — 4xx 는 백엔드 message 를 그대로
--------------------------------------------------------------------
지금 src/api/client.ts 가 오류 본문을 **읽지 않고** 상태코드별 고정 문구만
만듭니다. 그래서 admin-api 가 실어 보내는 한글 안내가 어느 화면에도
닿지 않습니다.

 [ ] 요구사항 1 — 응답 본문의 message 를 우선 사용
       서버가 message 를 주면 그것을, 없을 때만 상태코드별 기본 문구를.
       (admin-api 공통 응답 형태: { error, http_status_code, error_code,
        error_message, message })

 [ ] 요구사항 2 — 409 를 400 과 구분
       지금 409 가 "요청이 올바르지 않습니다."로 나옵니다.
       409 기본 문구: "이미 처리 중입니다. 잠시 후 다시 시도해 주세요." (28)

 [ ] 요구사항 3 — 타임아웃 여부를 오류 객체에 담기
       axios timeout 과 서버 504 를 화면이 구분할 수 있어야 B-3 이 가능합니다.
       (예: ApiError 에 timedOut: boolean 추가)

 [ ] 요구사항 4 — 화면 쪽 catch 에서 오류를 삼키지 않기
       CloudTransferPage 가 `.then(ok, () => false)` 로 오류 객체를 버리고
       FAIL_DESCRIPTION 한 문구로 덮습니다. 아래 세 액션 모두 해당합니다.
         · [클라우드 전송]      (row-send)
         · [클라우드 전송 중지] (row-stop)
         · 전송 모드 변경        (card-auto)
       같은 문제가 BatchHistoryPage · BatchDetailModal · BatchSchedulePage
       에도 있습니다(목록과 모달이 서로 다른 문구를 내는 상태).


B-2. 500번대 토스트 문구 규격
--------------------------------------------------------------------
  상태   화면 문구                                                  재시도 유도
  ------------------------------------------------------------------------
  500    "서버 내부 오류가 발생했습니다. 잠시 후 다시 시도해 주세요."   O
  503    "서버와 연결하지 못했습니다. 잠시 후 다시 시도해 주세요."      O
  504    "응답이 늦습니다. 처리 중일 수 있으니 새로고침해 확인해 주세요."  X (B-3)

  ※ 504 만 재시도를 유도하지 않습니다. 요청이 이미 들어가 처리 중일 수
     있어서, 다시 누르면 중복 전송·중복 실행이 됩니다.
  ※ 서버가 message 를 주면 그것을 우선합니다(B-1). 위는 기본 문구입니다.


B-3. 504 쿨링 — 버튼 60초 비활성화
--------------------------------------------------------------------
 [ ] 대상 액션 (요청이 들어갔을 수 있어 재클릭이 위험한 것)
       · 클라우드 전송 제어  [클라우드 전송]      — 행 단위
       · 클라우드 전송 제어  [클라우드 전송 중지] — 행 단위
       · 배치 이력          [긴급 재처리]        — 행 단위
       · 배치 상세 모달      [재처리]
       · 배치 스케줄        [바로 실행]          — 행 단위

 [ ] UI 처리
       1. 504(또는 timedOut) 응답을 받으면 **그 행의** 버튼만 60초 비활성
          (목록 전체를 잠그지 않습니다)
       2. 버튼 라벨에 남은 시간 표시 — 예: "전송 중… (42초)"
       3. 토스트는 B-2 의 504 문구
       4. 60초가 지나면 자동 해제. 목록 새로고침 시에도 쿨링은 유지
          (다른 탭에서 눌러도 중복이 나지 않도록)
       5. 쿨링 중에는 그 행의 상태 칩을 "확인 필요"로 두는 것도 방법입니다

 [ ] 왜 60초인가
       커넥터 read 60초가 사슬의 가장 안쪽입니다. 그 안에 끝나거나 실패가
       확정되므로, 60초 뒤에는 목록 새로고침으로 결과를 볼 수 있습니다.


B-4. nginx 프록시 타임아웃 75초
--------------------------------------------------------------------
 [ ] custom-nginx.conf 의 /api/ 블록에 proxy_read_timeout 75s 추가
       지금 이 블록에만 설정이 없어 기본 60초입니다. admin-api 의 커넥터
       대기(60초)와 같아 **nginx 가 먼저 끊을 공산**이 큽니다. 그러면
       admin-api 가 만든 504 본문 대신 nginx 의 HTML 504 가 화면에 갑니다.
       (같은 파일의 다른 블록들은 이미 300s 입니다)

 [ ] 화면 axios 타임아웃은 80초
       사슬의 가장 바깥이어야 합니다. 현재 공통 15초 · release 70초입니다.

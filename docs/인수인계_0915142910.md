## 1. 이 프로젝트가 뭘 하는가

교정 AI 플랫폼의 **비정형 음성 수집** 파이프라인입니다.
보라미(교정본부 시스템)의 수용자 음성을 가져와 STT 텍스트로 만들고 하류로 넘깁니다.

```
보라미 음성(접견·전화) → 수집 → 복호화 → STT → [비식별 커넥터] → PPP(대구)
                        └────── 이번 과제 범위 ──────┘
```

### 서비스 2개

| 레포 | 역할 | 배포 |
|---|---|---|
| `data_voice-collector-x2daarjxe4` | 음성 수집 배치 본체 | AI 플랫폼 K8s (`data-pipeline` ns) |
| `data_borami-xvarm-broker-1joiuorqhl` | 보라미 안에서 XVARM 을 대신 호출하는 얇은 REST 중계 | **개발계=K8s 파드 / 운영=보라미 서버에 단일 jar 수동 배포** |

브로커가 별도 레포·별도 배포인 이유: 운영 배포지가 우리 K8s 가 아니라 **교정본부 보라미 WAS 서버**입니다.
CI/CD 를 탈 수 없고(내부망), 발주처 제출 가능성이 있어 의존성을 최소로 유지합니다
(web + springdoc + lombok 뿐. DB·ORM 없음).

### ★ 가장 중요한 개념 — 접견과 전화는 완전히 다른 2트랙

이걸 모르면 코드가 안 읽힙니다.

```
[접견 MEET]  보라미 DB 4단 조인으로 키 획득
             → XVARM 브로커에 추출 지시 (REST)
             → XVARM 이 보라미 임시폴더에 파일 생성
             → ESB FILE2FILE(P20) 이 우리 스토리지로 동기화
             → 복호화(R플레이어 로직) → STT

[전화 PHONE] 단일 테이블(TB_IMPH_UCDR_DS) 조회
             → ESB 전화 전용 연계 프로바이더가 파일을 떨궈 줌
             → 복호화(ARIA-128/AES-256) → STT
             ※ XVARM·브로커를 타지 않는다
```

**전화는 브로커와 아무 상관이 없습니다.** 예전에 전화 파일 공급 모드가 브로커 스위치에
얹혀 있어서(`state.broker()==MOCK ? "MOCK" : "ESB"`) 브로커를 REST 로 올리면 전화까지
ESB 대기로 끌려가 조용히 실패했습니다. 지금은 `voice.phone.mode` 로 분리되어 있습니다.
**다시 합치지 마십시오.**

## 2. 개발 환경 — 여기서 대부분 막힙니다

### 2.1 Maven 이 PATH 에 없습니다

이 PC 에는 `mvn`·`java` 가 PATH 에 없습니다. JDK 는 `C:\Users\이현구\.jdks\temurin-17.0.19` 에만 있습니다.

```powershell
$sc = "<스크래치패드>"   # Maven 3.9.9 를 여기 풀어서 씁니다
$env:JAVA_HOME = "C:\Users\이현구\.jdks\temurin-17.0.19"
$env:PATH = "$env:JAVA_HOME\bin;$sc\apache-maven-3.9.9\bin;$env:PATH"
$env:MAVEN_OPTS = "-Dfile.encoding=UTF-8"
mvn -B -ntp -s .\settings.xml "-Dmaven.repo.local=C:\maven-repository" clean package
```

**`-Dmaven.repo.local=C:\maven-repository` 가 핵심입니다.**
기본 `~/.m2/repository` 는 아티팩트가 `central` 로 캐시돼 있는데 레포의 `settings.xml` 이
모든 것을 사내 Nexus(`msap-maven-public`)로 미러링해서, 리졸버가 repository id 불일치로 거부합니다.
`C:\maven-repository` 쪽은 Nexus 에서 받은 것이라 id 가 맞습니다.

- 사내 Nexus 는 사내망에서 도달 가능 → **온라인 빌드가 가장 확실**합니다.
- 오프라인(`-o`)은 플러그인 전이 의존성이 없어 실패합니다.
- Maven 배포본은 https://archive.apache.org/dist/maven/maven-3/3.9.9/binaries/apache-maven-3.9.9-bin.zip
  를 스크래치패드에 풀어 쓰면 됩니다.

### 2.2 helm / docker / node 없음

- `helm` 없음 → 필요하면 https://get.helm.sh/helm-v3.16.3-windows-amd64.zip 를 스크래치패드에 풀어 쓰십시오.

### 2.4 ★ 시뮬레이터 HTML 을 파이썬으로 편집할 때의 함정

`voice_collector_simulator.html` 을 python heredoc 으로 수정하다가 **두 번 깨뜨렸습니다.**

문제: python `"""..."""` 안의 `'\\n'` 이 파일에는 **실제 개행**으로 들어가
JS 문자열 리터럴이 줄 중간에서 끊깁니다 → `SyntaxError: Invalid or unexpected token`
→ 스크립트 전체가 죽어서 **트랙 영역이 통째로 빈 화면**이 됩니다.

대응:
- JS 문자열 안에 개행이 필요하면 `String.fromCharCode(10)` 을 쓰십시오.
- 수정 후 반드시 브라우저 콘솔로 확인:
  ```js
  const src = await fetch('/voice_collector_simulator.html').then(r=>r.text());
  const js = src.match(/<script>([\s\S]*)<\/script>/)[1];
  try { new Function(js); 'OK' } catch(e) { e.message }
  ```
- **주의**: 브라우저 콘솔 오류 버퍼는 페이지 이동해도 안 지워집니다.
  이전 로드의 오류가 계속 보이므로, 위 `new Function` 검사로 실제 상태를 확인하십시오.

### 3.4 EXEC_ID 채번 규약 — 건드리지 마십시오

로그 컬렉터가 `JOB_ID` 로 EXEC_ID 접두 3자를 정합니다.

```
EXEC_ID = yyyyMMdd(8) + 작업코드(3) + 회차(3)
   VOICE_ANALYSIS → VOC     TEST_BATCH → TST
   BORAMI_STRUCT  → STR     EXTERNAL_API → EXT
```

- 시뮬레이터 실행은 전부 `test=true` → `JOB_ID=TEST_BATCH` → `20260915TST001`
- 스케줄러 배치는 `VOC`
- 로그 컬렉터의 `DELETE /api/v1/logs/test-data` 가 `JOB_ID='TEST_BATCH'` 를 연쇄 삭제
- 삭제 SQL 에 `SUBSTRING(exec_id FROM 9 FOR 3)='TST'` 조건이 박혀 있어 **운영 배치는 절대 안 지워집니다**

## 5. 알려진 함정 (실제로 겪은 것만)

### 5.1 ★ 브로커 출력 경로 불일치 — 가장 많이 당했습니다

**증상**: 접견 배치가 300초 기다리다 `수신 파일 대기 타임아웃` 으로 실패.
브로커 콘솔에는 "추출 완료" 가 찍혀 있어 정상으로 보입니다.

**원인**: 브로커가 만든 파일이 수집기가 보는 폴더와 **다른 곳**에 있습니다.

```
브로커 기본 프로파일 출력 : <브로커레포>\work\xvarm_out\
수집기가 감시하는 곳      : <수집기레포>\work\voice_raw\meet\
```

**해결**: 브로커를 반드시 **`local` 프로파일**로 띄우십시오.
IntelliJ → Run/Debug Configurations → Active profiles: `local`
(또는 `BROKER_OUTPUT_DIR=C:/Projects/data_voice-collector-x2daarjxe4/work/voice_raw/meet`)

**예방**: 배치 전에 시뮬레이터 `[브로커 연결 확인]` 버튼을 누르면
두 경로를 대조해서 `⚠ 브로커 출력 경로와 우리 접견 수신 폴더가 다르다` 를 즉시 알려줍니다.

> **미완 개선안(사용자 승인 대기)**: 브로커가 응답으로 `filePath` 를 주므로, 그 경로에
> **파일이 실제로 존재하는데** 우리 수신 폴더엔 없으면 5분 기다리지 말고 즉시 실패시킬 수 있습니다.
> 운영에서는 브로커가 주는 경로가 보라미 서버 기준이라 우리 파일시스템에 존재하지 않으므로
> 이 조건에 안 걸립니다(= 안전). 구현 위치는 `VoiceCollectService.acquire()`.

### 5.2 포트를 잡고 있는 낡은 프로세스

IntelliJ 로 여러 번 띄우면 이전 프로세스가 포트를 물고 있습니다.
새 프로세스는 `Port 8082 was already in use` 로 기동 실패하는데, **낡은 프로세스가 계속 응답**해서
"분명 고쳤는데 왜 그대로지?" 가 됩니다. 실제로 이것 때문에 오진했습니다.

```powershell
Get-NetTCPConnection -LocalPort 8082 -State Listen | Select -Expand OwningProcess -Unique |
  ForEach-Object { Stop-Process -Id $_ -Force }
```

### 5.3 멱등 표식 때문에 "아무 일도 안 일어남"

같은 대상을 두 번 처리하지 않습니다(`work/voice_work/.processed/`).
모드를 바꾸고 다시 돌리면 **전부 건너뜀** 이 되어 브로커가 호출되지 않습니다.
→ 시뮬레이터 `[Mock 데이터 초기화]` 를 먼저 누르십시오.

## 6. ★ 지시받은 작업 (미착수)

사용자 원문 지시를 그대로 옮기고, 각 항목에 착수 지점을 붙였습니다.

### 6.1 [우선순위 1] 로컬 개발 환경 포트 충돌 방지

사내 타 서비스(agent-connector 8080, log-collector 8090)와 겹치지 않게 조정.

- `voice-collector` 로컬 포트를 **`8085`** 로 변경
- `borami-xvarm-broker` 는 **`8082` 유지**
- `application-local.yml` / `application-dev.yml` 교정

**착수 지점**

| 파일 | 현재 | 할 일 |
|---|---|---|
| `voice-collector/src/main/resources/application-local.yml:16` | `port: ${SERVER_PORT:8081}` | → `8085` |
| 같은 파일 `:6~13` 주석의 포트 배치표 | 8081 로 적혀 있음 | 8085 로 갱신 |
| 같은 파일 `:8` 시뮬레이터 URL | `localhost:8081/...` | `localhost:8085/...` |
| `application-dev.yml:14` | `port: ${SERVER_PORT:8080}` | **K8s 는 8080 이 맞습니다** — 차트 probe·Service targetPort 가 8080. 바꾸면 파드가 CrashLoop 처럼 보입니다. 로컬만 바꾸십시오 |
| `README.md:89` | `localhost:8081/voice_collector_simulator.html` | 8085 로 |
| `broker/src/main/resources/application-local.yml` | 8082 | 그대로 |

> ⚠ `application-dev.yml`(개발계 K8s)의 8080 은 건드리면 안 됩니다.
> 헬름 차트 `container.port`/`targetPort`/probe 가 전부 8080 이고
> Dockerfile 이 `EXPOSE 8080` 입니다. 사용자 지시의 "로컬 포트"는 local 프로파일을 뜻합니다.
> 혹시 dev 도 바꾸라는 뜻이었다면 차트 3곳(`values.yaml` container.port·service.targetPort,
> `deployment.yaml` probe, Dockerfile EXPOSE)을 같이 바꿔야 합니다 — **확인받고 하십시오.**

### 6.2 [우선순위 2] 비식별 커넥터(agent-connector) 잔재 제거

> ### ⚠⚠ 착수 전 반드시 확인할 것
>
> 이 지시는 **개발계획서 v2 의 확정 설계와 정면으로 어긋납니다.**
>
> 계획서 2.2 R&R 표: *"텍스트 비식별(AI-R) · PPP 전송 = agent-connector 담당, 재사용,
> voice-collector 는 재구현 금지"* 이고, 파이프라인은
> `voice-collector → POST /deid/connect → agent-connector → AI-R 비식별 → PPP(대구)` 입니다.
>
> 커넥터 호출을 제거하면 **voice-collector 는 STT 텍스트를 만들고 아무데도 보내지 않게 됩니다.**
> 즉 파이프라인이 끊깁니다.
>
> 사용자가 "잔재(殘滓)" 라고 표현한 것으로 보아, 의도가
> **(a)** 아키텍처에서 커넥터 연동을 아예 뺀다 인지,
> **(b)** 로컬에 커넥터가 없어 뜨는 경고·UI 카드가 거슬리니 화면에서만 치운다 인지
> 불명확합니다.
>
> **(b) 라면 UI 만 정리하면 되고 백엔드는 건드리면 안 됩니다.**
> 반드시 사용자에게 확인한 뒤 착수하십시오.

지시 원문:

1. **환경 변수 및 설정 삭제** — 모든 설정 파일에서 `agent.connector.*` 관련 항목 삭제
2. **백엔드 로직 정리** — 커넥터 호출·전송 스위치 체크하는 Dead 코드 및 클래스/메서드 완전 제거(또는 Deprecated)
3. **시뮬레이터 UI 및 경고 문구 삭제**
   - 화면 하단 `[비식별 커넥터 (하류)]` 카드 완전 삭제
   - `"배치 전 확인: 비식별 커넥터 전송이 켜져 있는데 주소가 없다..."` 경고 상자 완전 삭제

**영향 범위 (조사 완료 — 이 목록대로 손대면 됩니다)**

| 구분 | 파일 |
|---|---|
| 설정 | `application.yml:132-135` · `application-dev.yml:110-114` · `application-local.yml:113-118` · `application-prod.yml:30-32` 의 `voice.sink.*` 블록 |
| 타입 | `VoiceProperties` 의 `Sink` record 와 최상위 `sink` 컴포넌트 |
| 클라이언트 | `sink/DeidConnectorClient.java` (클래스 전체) |
| 호출부 | `VoiceCollectService` — `connector.send(...)`, SEND 단계(T2 step) 생성 |
| 상태 | `VoiceBatchController.status()` 의 `sink` 맵, `warnings()` 의 커넥터 경고 |
| 문서 | `OpenApiConfig` 설명 문구 |
| 화면 | `voice_collector_simulator.html` — `flagCard('비식별 커넥터 (하류)'...)`, `#downstream`, 경고 렌더 |
| 테스트 | `sink/DeidConnectorClientTest.java`(전체), `ResilienceE2ETest`·`VoiceCollectE2ETest` 의 sink 참조, 나머지 4개 테스트의 `VoiceProperties.Sink(...)` 생성자 인자 |

> `VoiceProperties` 는 record 라 컴포넌트를 지우면 **테스트 5개의 생성자 호출이 전부 깨집니다.**

### 6.3 [우선순위 3] 시뮬레이터 기본값·UX

1. **보라미 조회 기본값** → `DIRECT_JDBC`

   선택 즉시 별도 버튼 없이 백엔드 URL 반영

   - 진행 중 버튼 `disabled`, 완료 후 원복

**착수 지점**

| 항목 | 위치 |

| 스피너 | `call()` 함수가 이미 `#controls` 에 `.busy` 클래스를 붙였다 뗍니다. 이걸 확장하거나 `runBatch()` 에서 버튼별 스피너 처리 |

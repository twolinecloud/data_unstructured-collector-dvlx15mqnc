## 1. 이 기간에 처리한 장애

### 1.1 브로커가 배포되지 않던 원인 — 차트의 전략 설정 충돌

**증상**: 개발계에서 일배치를 돌리면 접견 5건이 전부 COLLECT 에서 실패하고 전화 5건만 성공했다.
전화 트랙은 XVARM·브로커를 타지 않으므로 "전화만 되는" 모양으로 보였다.

**원인**: ArgoCD 동기화가 이 한 줄로 실패하고 있었다.

```
Deployment.apps "borami-xvarm-broker-1joiuorqhl" is invalid:
spec.strategy.rollingUpdate: Forbidden: may not be specified when strategy `type` is 'Recreate'
```

차트 템플릿이 `rollingUpdate` 를 **무조건** 넣는데 브로커만 `update.type: Recreate` 였다
(다른 다섯 차트는 `RollingUpdate` 라 드러나지 않았다). PVC·Service 는 먼저 만들어지고
Deployment 만 거부되므로 결과는 **"Service 는 있는데 엔드포인트가 비어 있는"** 상태다.

```
$ kubectl -n data-pipeline get endpoints borami-xvarm-broker-1joiuorqhl
NAME                             ENDPOINTS   AGE
borami-xvarm-broker-1joiuorqhl   <none>      20h      ← 뒤에 파드가 없다
```

**조치** (`data_HelmChart` master `9c2babd`): `type` 이 `RollingUpdate` 일 때만 `rollingUpdate` 를 낸다.
`Recreate` 는 되돌리지 않았다 — PVC 가 `ReadWriteOnce` 라 RollingUpdate 면 새 파드가 볼륨을
잡지 못해 옛 파드와 맞물려 멈춘다.

**남은 일**: **Jenkins 파이프라인 재실행.** ArgoCD 가 `Target: HEAD` 를 보므로 push 한 커밋을 집어 간다.
성공하면 위 `get endpoints` 에 주소가 찍힌다. ⚠ 투라코가 차트를 재생성하면 이 수정이 되돌아갈 수 있다
(0915 문서 §5.5 와 같은 문제). 배포 후 또 같은 에러가 나면 템플릿부터 확인할 것.

**나머지 다섯 차트에도 같은 잠재 결함이 있다.** 렌더 결과가 바뀌지 않으므로 같은 조건문을 넣어 두는 것이
안전하지만, 이번에는 브로커만 고쳤다.

### 1.2 브로커에 못 닿을 때 무엇이 잘못됐는지 말하게 했다

위 증상에서 남는 메시지가 `ResourceAccessException: I/O error on POST … : null` 뿐이라 원인을 알 수 없었다.
`RestXvarmBrokerClient` 가 `ResourceAccessException` 을 잡아 바꿔 적는다.

```
XVARM 브로커에 붙지 못했습니다 (http://…/extract) — 브로커가 응답하지 않습니다 —
파드가 떠 있는지(K8s Service 에 엔드포인트가 붙었는지) 확인하십시오. [ConnectException]
```

이 한 줄이 T4 에 그대로 남으므로 이력만 봐도 원인을 안다. 주소를 못 찾은 경우(`UnknownHostException`)는
서비스명·네임스페이스를 보라고 따로 적는다.

**추가로** 시뮬레이터가 접견이 섞인 배치 직전에 브로커를 한 번 찔러 보고, 못 닿으면 **돌리기 전에** 경고한다.
막지는 않는다 — 경고를 보고도 돌려 보고 싶을 수 있고 프로브가 틀릴 수도 있다. [전화만 실행]은 건너뛴다.

### 1.3 원클릭 재처리 시나리오가 ④에서 타임아웃 나던 것

원인이 셋 겹쳐 있었다.

1. **잔여 데이터** — 수동으로 1~4 를 돌려 본 뒤 자동 실행을 누르면 멱등 표식이 남아 ②가 '건너뜀' 이 되고
   실패 이력이 안 남아 시나리오가 성립하지 않았다. → 시작 시 **초기화 후 재생성**.
2. **③→④ 동기화** — 주소만 바꿔 놓고 곧바로 ④를 돌리면 수신 파일 대기(20초)가 헛돌았다.
   → 브로커 프로브가 `reachable`·경로 일치를 말할 때까지 기다린 뒤 ④를 돌린다.
3. **창 이탈** ← 이것이 핵심이었다. 10분 주기 창은 실제로 **20분**(`periodic-lag-min`)인데,
   ①~③ 을 도는 사이에 지연 표본(접견 지금-18분)이 창 밖으로 밀려나 재처리 대상에서 빠졌다.
   재현했을 때 ④의 대상이 2건이 아니라 **1건**이었다.
   → 자동 실행은 ④를 **구간 지정(최근 `periodic-lag-min`+10분)** 으로 돌린다. 창을 좁게 잡아
   일배치 5건은 들이지 않으므로 "실패 2 → 재처리 2" 가 그대로 대응된다.

### 1.4 테스트가 외부 로그 컬렉터에 기대고 있었다

`VoiceCollectE2ETest` 가 `log-collector.enabled` 를 끄지 않아 `localhost:8090` 을 탔다.
그 포트가 **듣기만 하고 응답하지 않으면 호출마다 30초씩** 멈춰 빌드가 10분 넘게 늘어진다(실제로 두 번 겪었다).
`ResilienceE2ETest` 처럼 `log-collector.enabled=false` 를 준다.

같은 이유로 **지금 8090 로그 컬렉터가 응답하지 않는 상태로 보인다.** 그 상태로 배치를 돌리면 단계마다
30초씩 멈추므로 시연 전에 확인할 것.

## 2. 새로 붙은 기능

### 2.1 Agent Connector — 이관 적재 Mock · 비식별 바이패스 · T2 4→3단계

최종 이관 스펙(수신 측 API·포맷·인증)이 확정되지 않았다. 확정될 때까지 아무것도 안 하면 상류가 자기 구간을
끝까지 검증할 수 없다. 그래서 **이관의 마지막 한 걸음만 파일 쓰기로 대신한다** — 상류에서 보면 호출·응답·이력이
실제와 같고, 스펙이 정해지면 `AgentIngestStore` 의 저장 부분만 실제 전송으로 바꾸면 된다.

```
{base}/unstructured/meet    비정형 음성(접견)
{base}/unstructured/phone   비정형 음성(전화)
{base}/structured           정형 — 전송 직전 압축 조각
```

`base` 는 `agent.ingest.base-dir` 이 비면 OS 로 정한다 — Windows `C:/k8s/agent_connector` · 그 외 `/k8s/agent_connector`.

| API | 쓰임 |
|---|---|
| `POST /api/v1/pipeline/ingest/voice` | 수집기가 1차 저장 뒤 부르는 창구 |
| `GET /api/v1/pipeline/ingest/status` | 폴더 존재·쓰기 가능·적재 수 (헬스체크가 읽는다) |

> **접두를 `/api/v1/pipeline/` 으로 둔 이유**: admin-fe nginx 가 커넥터로 보내는 프리픽스 목록
> (`deid|transmit|ppp|pipeline|loadtest|mock`)이 고정돼 있다. 새 프리픽스를 만들면 admin-api 로 떨어져 404 다.

**정형은 옮긴다(move).** 복사하면 아카이브와 적재 폴더에 같은 조각이 둘 남아 재처리가 "아직 안 보낸 조각" 으로
오해한다. 볼륨이 다르면 복사 후 원본을 지워 같은 결과를 만든다.

**비식별 바이패스**: `deidentificationEnabled` **기본 `false`**. 꺼져 있으면 **룰 탐색 자체를 건너뛴다** —
`tasks` 가 비면 ADID/AIR 병렬 호출이 한 건도 나가지 않는다. 엔진 안쪽에서 분기하면 호출은 하고 결과만 버리는
모양이 되어 두 시스템이 죽어 있을 때 여전히 타임아웃을 먹는다. '시도하지 않는다' 가 요구사항이었다.
감사(`_audit`)에 `deidentificationEnabled` · `airMode=BYPASS` · `adidMode=BYPASS` 로 남겨,
나중에 "비식별된 줄 알았다" 가 되지 않게 한다. **기존 화면(deid_demo.html) 호출 2곳은 `true` 로 명시**했다.

**T2 4→3단계**: 운영 파이프라인의 T2 를 `COLLECT / CLEANSE / DEIDENT` 로 줄였다. 전송 단계가 이관 적재로
바뀌었으므로 SEND 행을 남기지 않고, 적재 결과는 T1 마감 메시지와 서버 로그에 남는다.
⚠ **재처리 시뮬레이터(`ReprocessService`)의 SEND 는 그대로 뒀다** — 'SEND 실패 → 재전송' 시연이 그 단계를 전제로 한다.

### 2.2 Voice Collector — 1차 저장 뒤 이관 호출

배치가 STT 결과를 `{ROOT}/xenon/{meet|phone}/{execId}/` 에 남긴 뒤(여기까지가 이 서비스의 완결)
커넥터의 이관 API 를 부른다. `deidentificationEnabled=false` 로 호출한다.

- **이관이 실패해도 배치는 성공이다.** 산출물은 이미 디스크에 있고, 못 넘긴 것은 폴더를 보고 다시 넘기면 된다 —
  이관 때문에 STT 를 다시 도는 것은 낭비다. 못 붙으면 경고만 남긴다.
- 건마다 부르지 않고 **배치 끝에 한 번에** 넘긴다. 건별 호출은 커넥터가 죽어 있을 때 건당 대기가 쌓인다.
- 주소는 환경 프리셋 — 로컬 `http://localhost:8080` · K8s `agent-connector-dp8qbi7xqh:8080`.

### 2.3 헬스체크 배지 5종 (상단 헤더)

`GET /api/v1/voice/health` 가 **서버에서 다섯을 한 번에 찔러** 내려준다. 화면이 직접 부르면 오리진이 달라
CORS 에 걸리고, K8s 서비스명은 브라우저가 풀 수도 없다.

| 배지 | 무엇을 보나 |
|---|---|
| DB | 지금 조회 모드가 가리키는 쪽(로컬 H2 / 개발계 PostgreSQL)에 실제로 붙어 본다 |
| ESB | 주소가 설정돼 있을 때만. ESB 모드가 아니면 회색 |
| 브로커 | 붙는지 + **출력 경로가 우리 수신 폴더와 같은지**까지 |
| 로그 컬렉터 | `enabled=false` 면 회색 |
| 에이전트 커넥터 | `ingest/status` 를 읽어 **적재 폴더가 쓸 수 있는지**까지 |

상태는 셋이다 — `UP`(초록·연결됨) · `DOWN`(빨강·연결 안됨) · `OFF`(회색·미사용).
**끈 것은 고장이 아니다**: Mock 브로커·미연동 로그 컬렉터는 회색이다.

**폴링 제어**: 자동 확인 **60초**, [연결 새로고침] 으로 즉시 확인.
**배치·재처리 시나리오가 도는 동안에는 멈춘다**(중첩 카운터) — 시험 중에 DB 커넥션·포트를 같이 건드리면
그 자체가 시험 결과를 흔든다. 멈춘 동안 배지가 흐려지고 "자동확인 멈춤(시험 중)" 이 뜬다.
서버는 같은 결과를 3초간 캐시해 연타·다중 탭의 몰림만 걷어 낸다.

## 4. 작업 규칙 (0917 문서에서 이어짐)

- 서비스 소스는 `feature/*` → `dev` 머지 → push (Jenkins 가 dev 를 배포). 헬름 차트는 `master`.
- 커밋 메시지에 `Co-Authored-By:` 등 AI 표기를 넣지 않는다.
- 사용자의 IntelliJ 인스턴스(브로커 8082 · 수집기 8085 · 로그 컬렉터 8090)는 **절대 죽이지 않는다.**
  검증용은 18081/18085/18086 등 다른 포트로 띄우고 끝나면 정리한다.
  ⚠ **18085 는 사용자가 `kubectl port-forward` 로 쓰고 있을 수 있다**(개발계 파드). 실제로 그것을 모르고
  붙었다가 검증 호출이 개발계로 간 적이 있다. 띄우기 전에 포트 점유를 확인할 것.
- 개발계 보라미 DB 포트포워딩은 사용자가 수동으로 `localhost:15433` 에 연다.
- 빌드는 `mvn -s .\settings.xml -Dmaven.repo.local=C:\maven-repository` 조합이어야 통과한다.
  ⚠ 검증 인스턴스가 `target/*.jar` 를 잡고 있으면 빌드가 막힌다 — 빌드 전에 내려둘 것.

## 1. EXEC_ID 접두사 VOC → UNS

### 1.1 누가 채번하나 — 로그 컬렉터

`LogService.createBatch` → `execPrefixOf(req)` → `DataTypeCd.prefixOf(dataTypeCd)`. 접두사는 **JOB_ID 가 아니라 데이터 구분(C01)** 이 정한다(`JOB_ID=TEST_BATCH` 만 `TST` 우선).
수집기는 음성(`VOICE_ANALYSIS`) · 이미지(`IMAGE_COLLECT`) 모두 `dataTypeCd=UNSTRUCTURED` 로 T1 을 연다 → 수집기 쪽 설정으로는 접두사를 바꿀 수 없고(지정 EXEC_ID 는 TST 포함 값만 허용),
**로그 컬렉터 `DataTypeCd.UNSTRUCTURED("비정형", "VOC")` → `"UNS"`** 로 바꿨다. 음성 · 이미지 모두 `yyyyMMdd + UNS + 회차3`(예 `20261002UNS001`), 시험은 `TST` 그대로.

### 1.2 기존 VOC 이력 · 다른 곳 영향

| 대상 | 영향 |
|---|---|
| 이미 쌓인 `…VOC…` 이력 | **그대로 둔다.** 로그 컬렉터 목록 · 대시보드는 `data_type_cd` 로 거르고, 시험 이력 정리는 `exec_id ILIKE '%tst%'` / `SUBSTRING(exec_id,9,3)='TST'` 만 본다 — 접두사로 운영 데이터를 고르는 SQL 은 없다(확인함) |
| 로그 컬렉터 주석 · Swagger | `STR/VOC/EXT` → `STR/UNS/PUB/LAW` (채번 표에 "2026-10-02 전 이력은 VOC") |
| 수집기 | 로컬 임시 ID(로그 컬렉터 미연동) — 음성 `yyyyMMdd+UNS+HHmmssSSS`, **이미지도 같은 모양**(예전 `IMG-yyyyMMdd-HHmmssSSS[-TST]`) · 가짜 로그 컬렉터 채번 · 테스트 예시 ID · 주석 · 설정 주석 · Swagger 예시 · 시뮬레이터 문구 |
| 그대로 둔 것 | 브로커 요청 키 `VOC-{execId}-{대상키}`(`XvarmBrokerClient`) — EXEC_ID 가 아니라 브로커 멱등 캐시 키의 접두라 바꾸면 캐시 키만 달라진다 |
| 다른 저장소(손대지 않음) | admin-api `db/sample/sample_data.sql` · README 의 `…VOC001` 예시, admin-fe `public/deid_demo.html` 의 `<option value="VOC">비정형 (VOC)</option>`(비식별 데모 화면 필터) — 기능 영향은 없고 표기만 옛값. 필요하면 각 담당에게 |

## 3. Admin DB C05 3단계 정비 — `src/main/resources/db/admin/V2__c05_unstructured_three_steps.sql`

| 코드 | 전 | 후 |
|---|---|---|
| COLLECT | 1 · Y | **1 · Y** |
| ANALYZE | 3 · Y | **2 · Y** |
| SEND | 6 · Y | **3 · Y** |
| CLEANSE | 2 · Y | 2 · **N** |
| DEIDENT | 4 · Y | 4 · **N** |
| STORE | 5 · Y | 5 · Y (지시 범위 밖 — 그대로) |

- **위치 · 적용 방식**: V1(`tb_src_inmate_photo`)과 같이 **앱이 실행하지 않고 관리자가 Admin DB(correction_ai · kcais)에 적용**한다. UPDATE 4문 · 바뀐 행만 갱신(멱등) · 되돌리기 SQL 은 파일 머리 주석.
  공통코드 표의 정본 Flyway 는 admin-api(`V1__create_common_code_tables.sql` … 현재 V19)다 — admin-api Flyway 로 관리하려면 같은 내용을 admin-api `V20__…` 로 옮긴다(스키마 접두 `kcais.` 는 admin-api 스크립트 관례대로 뺀다).
- **행은 지우지 않는다** — 옛 배치의 T2(DEIDENT 행)와 **정형 체인(COLLECT → CLEANSE → DEIDENT → SEND)이 지금도 이 코드값을 기록**한다(data-collector `StructuredIncrementalBatch` 의 `CLEANSE` 등).
- **영향**: 로그 컬렉터의 단계명 조인(`LogMapper` c5)은 `USE_YN` 을 보지 않는다 → 정형 배치의 CLEANSE · DEIDENT 단계명도 그대로 나온다. admin-api 공통코드 API(`commonCodeMapper` · `USE_YN='Y'`)의 C05 목록에서만 빠진다.
  배치 이력 화면의 단계명은 admin-fe 상수(`pages/pipeline/BatchHistory/constants.ts`)라 영향이 없다.
- **seed 주의**: 로그 컬렉터 `initCommonCodes` · `sql/kcais_seed.sql`, admin-api V1 은 여전히 6단계 · 전부 Y 로 넣는다. 기존 DB 에서는 `ON CONFLICT DO NOTHING` 이라 V2 를 되돌리지 않지만, **새 DB 를 seed 로 만들면 V2 를 다시 적용**해야 한다.
- 검증: `AdminC05MigrationTest` — admin-api V1 과 같은 표(제약 포함) · 행을 H2(PostgreSQL 모드)에 만들고 스크립트를 실제로 실행. 결과 · 다른 그룹 보존 · 두 번째 실행 무변경(멱등).

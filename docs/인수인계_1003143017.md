## 2. C05 3단계 마이그레이션 → 로그 컬렉터 V17 (지시 1)

### 2.1 V17

`log-collector src/main/resources/db/migration/V17__c05_unstructured_three_steps.sql` — 내용은 1002215121 3장과 같다.
COLLECT 1 · ANALYZE 2 · SEND 3 사용, CLEANSE · DEIDENT `USE_YN='N'`(행은 둔다 — 정형 체인 · 옛 T2 가 기록), STORE 그대로, 바뀐 행만 갱신(멱등), 되돌리기 SQL 은 머리 주석.

- **시드도 맞췄다** — `LogMapper.initCommonCodes` · `sql/kcais_seed.sql` 의 C05 를 V17 결과와 같은 값으로. 빈 DB 를 시드로 만들어도 6단계로 돌아가지 않는다.

- 테스트 `C05MigrationTest` — admin-api V1 과 같은 표 · 행(H2 PostgreSQL 모드)에 V17 을 실제로 돌려 결과 · 멱등 · 다른 그룹 보존 확인. (로그 컬렉터에 테스트 범위 H2 2.2.224 추가 — 수집기와 같은 버전, 새로 내려받지 않음)
- 수집기의 `db/admin/V2__c05_unstructured_three_steps.sql` · `AdminC05MigrationTest` 는 삭제(`2d971de`).

### 2.2 V16 미적용 DB 호환 (dev 머지 안전장치)

dev 머지는 곧 개발계 배포인데 V16(`tb_file_proc_log.step_type_cd`)은 관리자가 손으로 적용한다 — 새 빌드가 먼저 나가면 T4 INSERT 가 없는 컬럼을 써서 **전부 실패**했을 것이다.
그래서 로그 컬렉터가 `information_schema.columns` 로 컬럼을 확인해 **없으면 단계 없이 적재**하고 1분마다 다시 본다(`LogService.fileStepColumn`). V16 이 적용되면 재기동 없이 단계를 쓰기 시작한다. 확인 쿼리가 실패해도(권한 등) 적재는 막지 않는다.
매퍼 SQL 은 `LogMapperFileProcH2Test` 가 실제 매퍼 XML(운영과 같은 MyBatis 설정)로 V16 전 · 후 두 모양에서 적재 · 조회 · 집계를 돌려 확인했다.

- 마이그레이션 이력 표에는 기록하지 않았다 — admin-api Flyway(`flyway_schema_history`)에도 V16 · V17 번호가 따로 있어, 로그 컬렉터 스크립트를 거기 넣으면 번호가 겹친다.
- 되돌리기: V16 — `DROP INDEX kcais.ix_file_proc_log_03; ALTER TABLE kcais.tb_file_proc_log DROP COLUMN step_type_cd;` (로그 컬렉터는 1분 안에 '없음' 으로 돌아가지 않는다 — 한 번 '있음' 이면 캐시하므로 되돌릴 땐 로그 컬렉터 재기동) ·
  V17 — 파일 머리 주석의 원래 값(위 '적용 전' 열).

## 1. 한 줄 요약

시험용 더미 데이터의 "**딱 한 번만 일부러 실패하기**" 기능이, 서버가 다시 켜지면 그 사실을 잊어버려 **한 번 더 실패**하던 문제를 고쳤다.
이제 "이미 한 번 실패했다" 는 기록을 **디스크(PV) 파일에 적어 두기** 때문에 서버가 다시 켜져도 기억한다.

---

## 2. 무슨 기능인가 — "한 번만 실패하는 더미"

시뮬레이터에서 대시보드·배치용 더미(DMY)를 만들 때 장애 건수를 넣으면, 일부 건의 이름(키)에 **표식**이 붙는다.

| 표식 | 뜻 | 일부러 실패하는 곳 |
|---|---|---|
| `CF` | COLLECT_FAIL | 수집 단계 |
| `AF` | ANALYZE_FAIL | 정제/분석(STT) 단계 |
| `SF` | SEND_FAIL | 적재/전송(제논) 단계 |

예) `DMY-MEET-20261002-SF-0003` → 이 접견 녹음은 **전송 단계에서 실패**한다.

이 기능의 목적은 "**실패 → 긴급 재처리 → 성공**" 흐름을 보여 주는 것이다.
그래서 표식 건은 **처음 한 번만** 실패하고, 두 번째(재처리)부터는 통과해야 한다.
이를 위해 서버는 "이 키는 이미 한 번 실패시켰다" 는 **메모(소진 기록)** 를 남겨 둔다.

---

## 3. 무엇이 문제였나

그 메모를 **서버의 기억(메모리)** 에만 적어 두었다.

비유하면 — 칠판에 "이 사람은 이미 한 번 떨어뜨렸음" 이라고 써 두었는데, **서버가 다시 켜질 때마다 칠판이 지워지는** 상황이다.
칠판이 지워지면 서버는 그 사람을 처음 보는 것으로 알고 **또 떨어뜨린다**.

개발계(쿠버네티스)에서는 서버가 생각보다 자주 다시 켜진다 — **dev 브랜치에 무언가 머지될 때마다(문서만 고쳐도) 새로 배포**되기 때문이다.
실제로 2026-10-03 개발계에서 긴급 재처리를 확인할 때:

1. 처음 실행 → 표식 건 실패(정상)
2. 그 사이 문서 커밋 머지로 서버가 **두 번** 다시 켜짐
3. 재처리 → **또 실패**(칠판이 지워졌으니까) → 재처리 → 또 실패 → 세 번째에야 성공

그래서 개발계에 쓸모없는 실패 이력이 몇 건 더 쌓였다(직전 문서 10장).

---

## 4. 어떻게 고쳤나

메모를 칠판(메모리)뿐 아니라 **공책(디스크 파일)** 에도 적는다.

- 공책 위치: **`{ROOT}/mock/scenario_faults.json`**
  - 개발계: `/k8s/unstructured_collector/mock/scenario_faults.json` (수집기 PV — 파드가 바뀌어도 남는 저장소)
  - 로컬: 설정한 ROOT 아래 같은 경로
- **서버가 켜질 때** 공책을 읽어 칠판에 다시 옮겨 적는다 → "이미 한 번 실패했다" 를 기억한다.
- **메모가 생기거나 지워질 때마다** 공책 전체를 새로 쓴다.
  - 새 종이(임시 파일)에 다 쓴 뒤 바꿔 끼우는 방식이라, 쓰는 도중에 서버가 죽어도 반쯤 쓴 공책이 남지 않는다.
- 공책을 못 읽거나 못 써도(디스크 문제 등) **배치는 멈추지 않는다.** 경고 로그만 남기고 예전처럼 칠판(메모리)만으로 계속한다.
- **운영(prod)** 에서는 이 기능 자체가 꺼져 있다 — 공책도 읽거나 쓰지 않는다.

공책 내용은 이렇게 생겼다(사람이 열어 봐도 알 수 있다):

```json
{
  "COLLECT_FAIL|DMY-MEET-20261002-CF-0001" : "2026-10-03T15:48:11",
  "SEND_FAIL|DMY-MEET-20261002-SF-0002" : "2026-10-03T15:48:11"
}
```
= "이 키는 이 단계에서 이 시각에 이미 한 번 실패시켰음".

## 5. 이제 어떻게 동작하나

| 상황 | 예전 | 지금 |
|---|---|---|
| 처음 실행 | 표식 건 실패 | 표식 건 실패 (같음) — 공책에 기록 |
| 재처리(서버 그대로) | 성공 | 성공 (같음) |
| 재처리(**그 사이 서버가 다시 켜짐**) | **또 실패** → 한 번 더 재처리해야 성공 | **바로 성공** |

### "다시 실패하게" 하고 싶을 때

같은 더미로 실패 시나리오를 한 번 더 보고 싶으면 기록을 지우면 된다. 지우면 공책에서도 지워진다.

- API: `DELETE /api/v1/mock/sim-data/scenario-faults` (용도만: `?target=DASHBOARD` 또는 `SIMULATOR`)
- 또는 시뮬레이터 상단 **[대시보드 테스트 데이터 초기화]** / **[시뮬레이터 데이터 초기화]** — 그 용도의 기록도 함께 지운다
- 지금 기록 보기: `GET /api/v1/mock/sim-data/scenario-faults` → `consumed`(건수) · `file`(공책 경로) · `rows`(키 목록)

## 7. 알아 둘 것

- 공책은 **DMY · SIM 더미의 표식 건**만 적는다. 실제 운영 데이터와는 상관없다(키 이름에 표식이 없으면 아예 대상이 아니다).
- 시뮬레이터에서 ROOT(디렉터리)를 바꾸면 그 뒤로는 새 ROOT 아래 공책에 쓴다. 읽기는 서버가 켜질 때 한 번이다.
- 개발계 PV 에 이미 처리된 옛 DMY 기록은 이번 배포 전 메모리에만 있었으므로 공책에 없다 — 다음 장애 시연부터 적용된다.
- 되돌리고 싶으면: 이 커밋(`198ef12`)을 되돌리면 예전처럼 메모리만 쓴다. 공책 파일은 지워도 되고 남아 있어도 해가 없다.

## 1. 쉬운 설명

**현황(바꾸기 전)**: 관리 화면에서 주기를 10분으로 저장하면 admin 이 곧바로 알려 주지만 첫 실행은 10분 뒤였다. 그 뒤로는
'시작 시각 + 10분' 마다 돌았다(Spring PeriodicTrigger 는 '발화가 끝난 시각 + 주기' 인데 발화가 실행기에 넘기고 곧바로 돌아오므로).
이전 배치가 아직 돌면 그 회차는 건너뛰어 겹쳐 돌지는 않았다.

**정형(data-collector)**: 등록 즉시 1회(PeriodicTrigger 첫 발화) + 배치를 스케줄러 스레드에서 끝까지 돌려 '끝난 시각 + 주기'.
파드 간 중복은 Admin DB `pg_try_advisory_lock(42120001)` 로 막아 기동 때 바로 돌아도 안전하다. 외부데이터 수집기는 관리 화면에서
사용 여부만 읽고 시각은 yml 크론이라 해당 없음.

**지금(바꾼 뒤)**:

```
관리 화면 저장(주기 10분) ──▶ 즉시 1회 ──(배치 끝)──▶ +10분 ──▶ 실행 ──(배치 끝)──▶ +10분 …
                                 │
                       다른 배치 · 다른 파드가 돌고 있으면 건너뛰고 지금 + 10분
```

- 배치 동안 스케줄러 스레드(1개)를 붙잡지 않는다 — 배치가 끝나면 다음 회차를 한 번짜리로 예약한다(5분 재조회가 멈추지 않게).
- 설정이 또 바뀌면 세대 번호가 올라가 이전 사슬은 다음 회차를 걸지 않는다.
- 잠금은 실행기가 접수할 때 잡고 배치가 끝나면 푼다 — 스케줄 · 바로 실행 · 긴급 재처리 모두. 롤링 배포(maxSurge 1) 중 옛 파드가
  돌리고 있으면 새 파드는 잠금을 못 잡아 건너뛴다(다음 회차에 돈다).

**자정 구간**: 주기 창은 '오늘 00:00 ~ 지금' 이고 자정 직후에만 고정 20분을 거슬러 봤다. 관리 화면은 10분 ~ 12시간을 고를 수 있어,
주기가 30분 이상이면 어제 마지막 회차 이후 ~ 자정 사이 건이 다음 창에 들어오지 않았다(예: 30분 주기 23:30 → 00:00 회차가 23:40 부터 →
23:30 ~ 23:40 빠짐). 회의(2026-09-11 · `ref/음성 043_STT.md` 19:01) 계획 "10분 단위 … 앞에서 못 돌리는 것까지 다 하고 20분 전" 의
'주기 + 10분' 으로 바꿨다. 배치가 10분보다 오래 걸리거나 자정을 낀 회차가 통째로 실패하면 여전히 빌 수 있다 — 그때는 [바로 실행]
(워터마크 ~ 지금)으로 메운다(POC 범위).

## 4. 주의

- 개발계는 `VOICE_SCHEDULE_ENABLED=false` 라 주기 값을 바꿔도 자동 실행은 없다(설정만 받음). 켜는 것은 사용자 결정.
- 실행기 밖의 동기 API(시뮬레이터 · `/api/v1/voice/**` · `/api/v1/image/**` 수동 · 성능 시험)는 DB 잠금을 쓰지 않는다 — 사람이 부르는 시험용.
- 로컬 검증 인스턴스를 개발계 Admin DB(PostgreSQL)에 붙이면 개발계 파드와 같은 잠금을 다툰다 — 같은 원천을 두 곳이 동시에 처리하지 않게 막는 것이라 맞는 동작.
- admin 은 다음 실행 예정 시간을 주기일 때 표시하지 않기로 했다(PL) — 시간 API 불필요.

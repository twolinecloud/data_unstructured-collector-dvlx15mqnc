# 클라우드 전송 — 단건 독립 전송 회귀 (2026-10-19)

> PL 최종 협의. 2026-10-16 ~ 10-18 의 **순차 체인**(누른 배치 이전의 전송 미완료 배치를 함께 보내기)을
> 폐기하고 **고른 한 건만** 보내는 방식으로 되돌렸다.

---

## 1. 왜 되돌렸나

체인은 누른 배치 이전의 전송 미완료 배치(실패 · 부분성공 · 취소 · **대기**)를 오래된 순으로 함께 보냈다.
그중 **대기(WAIT)** 는 비식별 결과를 사람이 검수하라고 **전송 가드가 멈춰 둔 건**이다.
체인이 그것까지 끌어다 보내면 **미검수 유출**이 된다.

화면 팝업("하위 대기 건을 모두 확인했습니까?")으로 승인을 받는 방식이었지만, 누르는 사람이
**하위 몇 건이 무엇인지 알 수 없어** 승인이 형식에 그친다.

순서가 섞여도 된다 — 비정형(음성)은 파일 단위로 독립해 쌓이는 **append-only** 구조라
배치 간 선후가 데이터 정합성을 만들지 않는다. 이전 미완료 건은 각자 목록에서 눌러 보내면 된다.

## 2. 바뀐 코드 (수집기)

| 무엇 | 전 | 후 |
|---|---|---|
| `CloudSendService.Plan` | `(execId, sendStsCd, predecessors, requestedBy, triggerBy)` + `chain()` | `(execId, sendStsCd, requestedBy, triggerBy)` |
| `plan()` | `logCollector.sendChain(id)` 조회 후 이전 배치 수집 | **조회 자체를 하지 않는다** |
| `execute()` | `for (String id : p.chain())` 루프 | 한 번만 `processPending` |
| 202 응답 | `{… chain:[…]}` | `{… originExecId, sendStsCd}` — **`chain` 없음** |
| `LogCollectorClient.sendChain` | 있음(basis=SEND) | **제거** — 호출처 없음. 자리에 사유를 주석으로 남김 |
| 시뮬레이터 8번 탭 ③ | [연속 전송 실행] + "하위 대기 건 확인?" 팝업 | **[클라우드 전송 실행 (단건)]** · 팝업에서 그 질문 제거 |

**건드리지 않은 것** — 긴급 재처리의 체인(`failed-chain?basis=PENDING`)은 그대로다.
그쪽은 같은 배치를 **처음 단계부터** 다시 돌리는 것이고 전송 가드가 여전히 대기를 막아 주므로 이 문제가 없다.

## 3. admin-api 는 바꿀 것이 없다 — 이미 단건이다

코드를 따라가 확인했다.

```
어드민 화면(admin-fe)
  CloudTransfer/api.ts → POST /cloud-sends/{execId}/release        ← execId 하나
      ↓
admin-api CloudSendController.release(execId)
  → CloudSendService.release(execId)
      → agentConnectorClient.releaseHold(execId, triggerBy)        ← execId 하나
          ↓
에이전트 커넥터 POST /api/v1/transmit/holds/{execId}/release
```

- **admin-api 는 수집기의 `/internal/batch/cloud-send` 를 부르지 않는다.** 체인은 거기에만 있었고,
  운영 경로에는 연결되어 있지 않았다 — 시뮬레이터 8번 탭에서만 불렀다
- 따라서 **admin-api 변경 불필요.** 호출 규격(`{execId}` 하나)도 그대로
- 어드민 화면도 응답의 `chain` 을 읽지 않는다(`CloudTransfer/api.ts` 확인) → `chain` 제거의 영향 없음

> 개발계 admin-api 는 `feature/propagate-4xx-message` 브랜치(`5a6a45b`)가 배포돼 있다.
> 그 브랜치에서도 release 경로는 단건이라 이번 변경과 무관하다.

## 4. 그런데 갭이 하나 있다 — 장부에 없는 실패 배치

커넥터 `release` 는 **보류 장부에 있는 건만** 보낸다. 장부에 없으면 **404** 다(커넥터 Swagger 명시).

장부에 없는 전송 실패 배치 — 커넥터에 **닿기 전에** 실패한 건(커넥터 5xx · 연결 실패) — 은
**수집기가 같은 EXEC_ID 로 다시 열어 전송부터** 돌려야 한다. 그 경로는 수집기 `cloud-send` 에만 있다.

어드민 대기 목록 12건을 커넥터 보류 장부(11건)와 맞대어 봤다.

> 실제 release 를 눌러 확인하지는 않았다 — 그건 외부(제논)로 데이터를 보내는 동작이다.
> 장부에 없다는 사실과 커넥터 명세(404)로 입증했다. 실제 확인이 필요하면 알려 주시면 누른다.

### 이건 이번 변경 때문이 아니다

체인 시절에도 **어드민은 체인을 안 썼다**(수집기 API 를 안 불렀으므로). 즉 이 갭은
2026-10-16 체인 도입 전부터 있었고, 단건 회귀로 **새로 생기지도, 없어지지도 않았다.**

### 선택지

| # | 방법 | 비고 |
|---|---|---|
| 1 | admin-api 가 **404 일 때 수집기 `cloud-send` 로 폴백** | 화면 변경 없음. admin-api 담당자 작업 |
| 2 | admin-api 가 처음부터 수집기 `cloud-send` 를 부른다(수집기가 장부 유무를 보고 갈라 줌) | 분기 한 곳으로 모임. 수집기 쪽 준비는 이미 됨 |
| 3 | 그대로 둔다 — 장부에 없는 실패는 **긴급 재처리**로 처리 | 화면 안내만 필요(지금 400 문구가 이미 그렇게 유도한다) |

수집기는 1 · 2 어느 쪽이든 **지금 그대로 받을 수 있다**(단건 규격 · `chain` 없음).

## 6. 배포가 한 번 실패했다 — 코드가 아니라 레지스트리

`dfbcdad` 를 올렸는데 30분이 지나도 개발계가 직전 커밋(`da9a974`)이었다. Jenkins 로그를 보니
**코드는 전부 통과**하고 마지막 단계에서 깨졌다.

| 단계 | 결과 |
|---|---|
| Maven | **BUILD SUCCESS** · 테스트 395개 통과 |
| podman build | **성공** — 12 STEP 전부, `…-dfbcdad` 태그까지 |
| **podman push** | **실패** |

```
Error: writing blob: uploading layer chunked:
       received unexpected HTTP status: 500 Internal Server Error
ERROR: script returned exit code 125 → Finished: FAILURE
```

Harbor(`registry.turacocloud.com`)가 blob 업로드를 거절한 것이다. **코드와 무관한 인프라 오류**다.

재시도(`856c9e6`)도 **같은 지점 · 같은 오류**였다. 일시적인 것이 아니다.

### 원인 — Harbor 의 Redis 가 디스크에 못 쓴다

Harbor 상태 API(`GET /api/v2.0/health`, 인증 없이 열려 있다)를 찍어 보니 바로 나왔다.

```
전체 상태: unhealthy
  core healthy · database healthy · jobservice healthy · portal healthy
  registry healthy · registryctl healthy
  redis  **unhealthy**
    MISCONF Redis is configured to save RDB snapshots, but it's currently unable to
    persist to disk. Commands that may modify the data set are disabled, because this
    instance is configured to report errors during writes if RDB snapshotting fails
    (stop-writes-on-bgsave-error option).
```

Redis 가 RDB 스냅샷을 디스크에 쓰지 못해 **쓰기 명령을 전부 거부**하고 있다.
Harbor 는 chunked blob 업로드 **세션 상태를 Redis 에 둔다** — 그래서 `podman push` 가
layer 를 올리는 중에 500 이 된다. `registry` 자체는 healthy 라 증상이 "레지스트리 장애" 처럼
보이지 않는 것이 함정이다.

**인프라 조치 사항**(우리 소관 밖)

| # | 할 일 |
|---|---|
| 1 | Redis 가 RDB 를 쓰는 **디스크 여유 확보** — 가장 흔한 원인이 꽉 찬 디스크다 |
| 2 | Redis 로그에서 bgsave 실패 사유 확인(권한 · 마운트 · 용량) |
| 3 | 급하면 `stop-writes-on-bgsave-error no` 로 쓰기를 열 수는 있다 — **다만 스냅샷 실패를 덮는 것이라 권장하지 않는다** |

> 기록해 둔다 — 나는 처음에 **import 순서나 Sonar 를 의심**했다. 둘 다 아니었다.
> 배포가 안 되면 추측하지 말고 **Jenkins 로그의 마지막 성공 단계**를 먼저 보고,
> 그다음 **그 단계가 의존하는 외부 상태**(여기서는 Harbor health)를 확인해야 한다.
> (import 순서는 실제로 어긋나 있어서 따로 바로잡았지만, 배포 실패와는 상관이 없었다.)
